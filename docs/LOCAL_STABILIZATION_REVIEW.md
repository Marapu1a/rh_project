# Ограниченная проверка локального контура

19.09.2026. Проверены Short/Monthly workers, общий CLI и существующие тесты.
Это проверка локального MVP, не полный аудит контрактов и не допуск к реальным средствам.

## Найдено и исправлено

1. Оба worker ожидали `tx.wait()` без срока; остановка проверялась только между
   шагами. Pending-транзакция могла удерживать запуск неопределённо долго.
   Общий `local-receipt.cjs` ограничивает ожидание 30 секундами и принимает AbortSignal.
   Timeout сообщает hash и прекращает запуск; abort возвращает stopped с hash.
   Ни тот, ни другой не отменяет и не переотправляет транзакцию. После её подтверждения
   новый запуск продолжает публикацию по состоянию контракта.
2. До begin принимался cutoff возрастом 256 блоков относительно текущей вершины.
   В следующем блоке он уже недоступен для EVM blockhash. Теперь preflight учитывает
   следующий блок: 255 допускается, 256 отвергается до отправки. Долгое включение
   транзакции всё ещё может привести к отказу контракта; preflight не гарантирует inclusion.

Пять регрессий воспроизводили ошибки до исправления: граница cutoff для обоих workers,
abort и timeout каждого worker. Pending создаётся отключением automine; тест проверяет,
что транзакция остаётся единственной ожидающей и после mining следующий шаг — публикация.
Артефакты этих регрессий синтетические; реальный локальный BUY покрыт отдельным сквозным тестом.

## Слабые решения, оставленные явно

| Место | Последствие | Следующий способ укрепления |
| --- | --- | --- |
| Повторное полное чтение/пересчёт dataset на шагах и ожиданиях | Нагрузка растёт вместе с историей и числом порций | Разделить неизменяемую проверку job и чтение progress; кэш с проверкой canonical anchor |
| Несколько чтений latest без общей фиксации блока | Конкурентное продвижение/reorg может дать несогласованный снимок и отказ | Один block tag для набора чтений, повторная проверка перед отправкой; Short recover уже фиксирует head |
| Single-job worker, нет постоянного scheduler | Сам не создаёт следующий job/cutoff и не закрывает пустые draining epochs | Отдельный последовательный scheduler с явными причинами ожидания |
| Нет durable mempool journal | Timeout сам по себе не определяет судьбу tx; неизвестный pending требует проверки | Сохранять hash/nonce до следующего действия, восстанавливать статус без слепой повторной отправки |
| Большой общий integration test | Хорошее покрытие связи модулей, но грубая локализация сбоя | Добавлять узкие отказные регрессии на найденные проблемы, как в этом шаге |

Ограничение receipt не ограничивает каждый RPC-вызов и broadcast. Полноценное прекращение
сетевой операции и автоматическое восстановление после падения процесса пока не обещаются.
Проверка pending nonce не является блокировкой между несколькими процессами.

## Границы перед реальными средствами

- Publisher определяет полноту snapshot; независимый replay обнаруживает расхождение,
  но не предотвращает его on-chain.
- RNG в локальных контроллерах тестовый. Finality/future-round binding остаётся открытым;
  проверенный отдельно криптографический verifier эту задачу сам не решает.
- Readiness проверяет локальные условия request, а не запас газа на весь draw.
- Creator income, конвертация и эксплуатационное пополнение ещё не соединены с контуром.

В этом шаге призовая математика, контракты и продуктовые правила не менялись.
Следующий небольшой технический приоритет — согласованное чтение состояния workers;
полноценный scheduler и production RNG требуют своих отдельных шагов.
