# Сверка двух ответов GPT: graduation и атрибуция покупки

02.10.2026. Получены commits `2d4caa8` и `5f3c497`; fast-forward затронул только
GPT_REVIEW_RESPONSE, локальные пакеты индексатора сохранены. Прочитаны
[первое исследование](archive/GPT_REVIEW_RESPONSE_GRADUATION_FIRST_2026-10-02.md)
и [последующее уточнение](GPT_REVIEW_RESPONSE.md). GPT исследовал код2038a57;
последующие локальные bounded cache/checkpoint/checksum пакеты он **не проверял**.

Здесь сверка с кодом, PRODUCT_SPEC и сохранёнными receipts; новые live RPC/trace,
fork и продуктовые tests не запускались. Внешние утверждения GPT не считаются
независимо подтверждёнными этой сверкой. Runtime и правила продукта не изменены.

## Что принимаем в технический план

| Вывод | Сверка / действие |
|---|---|
| Нужен EOA → AllowanceHolder → Settler → целевой USDG/Pons pool BUY | В нашем capture прямые AllowanceHolder примеры Harmonic `0xd3f689…` и PRIORS `0x6a272f…` — SELL. Signed deltas и pool currency order проверены повторно. Найти/исполнить именно BUY, не объявлять существующий пример достаточным |
| Harmonic EntryPoint BUY не доказывает USDG basis | Capture `0x764d4c88…`: native ETH quote, внешний bundler/Settler. Pool delta не доказывает debit smart account, а тем более USDG-покупку. Нужен отдельный proof ветки; trace конкретной tx — кандидат, доступность не проверена |
| Событие обнаружено ≠ билеты начислены | Разделять candidate, route proof и carry/attempts. Не выдавать Transfer TOKEN или HookFeeCollected за доказательство плательщика/покупки |
| Учёт одной оплаты не должен задваиваться | Candidate event identity уже есть. Для вложенных вызовов надо связать уникальные платежи с одной execution branch; общий tx balance нельзя раздать нескольким покупкам |
| Нельзя сортировать покупателей по возрасту/названию кошелька | Возраст, код на адресе и имя MetaMask не критерии принятого продукта. Подтверждённый self-batch уже допускает исполнение с кодом. Поддержка конкретного account implementation требует proof, а не эвристики |
| Дата sweep/claim не определяет билет | Согласуется с текущим разделением BUY/attempts и фактического prize funding. Pending TOKEN не считается USDG-бюджетом |

## Где уточняем ответ

- GPT приписывает `scripts/pons-zeroex-evidence.cjs` подстановку `tx.to` для nested
  trade. В текущем файле этого нет: он проверяет исходный target=AllowanceHolder,
  читает outer/inner calldata и выдаёт `admission: NOT_IMPLEMENTED`. Это неточная
  ссылка/описание, не найденный bypass runtime. Общий запрет использовать forensic
  вместо admission правильный; искусственно менять envelope для допуска нельзя.
- Trace не объявляем обязательным для **всех** ERC-4337 маршрутов. Для рассмотренного
  native/multi-op случая текущего receipt недостаточно; способ доказательства зависит
  от закреплённой реализации и исполнения. Public callTracer/withLog не подтверждены.
- Рекомендации exact-output/refund — сценарии исследования/отказа, не требование
  сразу поддержать все варианты. Первый adapter ограничиваем доказанным exact-input
  маршрутом, если именно такой будет получен; остальные получают явный отказ.
- Предложение smart account как участника соответствует направлению proof-based
  учёта, но не включает ERC-4337 в действующий admission. Нужны конкретный профиль,
  совпадение payer/recipient и публикация правил до активации.
- Включение комиссий в USDG basis уже принято. Fee, входящую в wallet debit, нельзя
  прибавлять к нему второй раз; TOKEN hook fee и gas не являются дополнительным USDG
  расходом. Связь refund с конкретной покупкой должна быть доказана.
- Чужие pools, общий split и распределение общей комиссии между legs не включаем
  технической правкой. Это отдельная продуктовая граница. Сейчас достаточно следовать
  согласованному Pons venue; нового решения владельца для продолжения не требуется.

## Ближайший пакет

1. Получить/воспроизвести EOA → AllowanceHolder → pinned Settler → **один целевой
   USDG pool** → тот же пользователь. Сохранить calldata/actions, исторические code
   hashes, receipts и баланс/платежи. Не форсировать желаемый pool подменой receipt.
2. Доказать exact basis: расход этой покупки с её комиссией минус её refund.
   Убедиться, что forwarded taker, плательщик и получатель однозначны. Если доказательства
   недостаточны — назвать пробел; trace не имитировать и безопасность не угадывать.
3. Если proof получен: отдельный versioned adapter → policy/index/API, без изменения
   старых genesis. Проверить 101 USDG → Short1/Monthly1 + carry1, SELL/другой pool/split,
   иной recipient, неоднозначные transfers/refunds и две покупки с общими средствами;
   повтор и reorg не удваивают учёт, frozen обязательства не переписываются.

Это один осмысленный пакет с условием допуска по доказательствам, не автоматическое
разрешение произвольного 0x. Потом — конкретный account/EntryPoint маршрут и адресные
traces при необходимости; пользовательские причины unsupported идут вместе с поддержкой.
Наблюдение до finality требует отдельного UI/feed: текущий finalized index нельзя
объявить уже реализованным pending feed на основании рекомендации GPT.

Полезный результат review — более точная исходная транзакция и границы proof.
Нового подтверждённого EOA USDG BUY или доступного trace GPT не принёс; это наша
следующая проверяемая задача. Operator permissions/SLA остались внешней зависимостью,
а не исправлением, которое можно сделать в нашем индексаторе.
