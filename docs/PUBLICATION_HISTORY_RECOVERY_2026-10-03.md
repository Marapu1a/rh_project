# История публикаций: остановка и холодное восстановление

03.10.2026. Проверка существующего исполнения на локальной EVM31337.
Runtime, контракты и продуктовые правила не менялись; расширен только
`scripts/benchmark-scheduler-load.cjs` флагом `--history-outage`.

## Сценарий и что именно проверяется

Два вручную опубликованных synthetic frozen job, реальные локальные Short/Monthly
controllers, общий scheduler, Pons transaction journal/gas budget. Mock RNG и USDG.
У Short и Monthly одинаковый набор разных кошельков с1–20 попытками на адрес.
Это не большой Pons/BUY/index/API прогон и не публичный архивный RPC.

После начала обработки останавливаем отправки, сохраняем прогресс и файлы.
Каждый сбой воспроизводится **в новом Node-процессе** без process-local proof:

| Сбой чтения | Вводимое повреждение |
|---|---|
| RPC error | Чтение первой publication tx выдаёт SERVER_ERROR |
| Missing calldata | Последняя publication tx каждого вида возвращает null; перед этим читается предыдущий префикс |
| Missing logs | Исторические события контроллеров возвращаются пустым списком |
| Bad calldata | Первая publication tx каждого вида имеет data=0xdeadbeef |

Перехват делается на методах ethers provider в тестовом дочернем процессе.
Фиксируются обращения к fault, ошибка проверяется на ожидаемую причину;
eth_sendTransaction/eth_sendRawTransaction считаются отдельно. Родитель сверяет
nonce, nextChunk обоих draw, все части vault и побайтное равенство main/scheduler
journals. Отказ не заменяется сохранённым verified flag.

Затем ещё один новый процесс читает полную историю без fault, продолжает те же
jobs. Общий исполнитель доводит оба draw до terminal и выплачивает награды.
Результат сверяется с независимыми моделями, балансом каждого победителя,
vault.reward=0, уникальностью hash и nonce delta. Повторный idle и восстановление
ранних файлов после выплат также обязаны дать0 новых отправок.

## Результаты

Малый100-wallet smoke PASS: все4 отказа без отправок и изменения журналов,
последующее завершение и restore. `.local/logs/scheduler-load-100-Bs8nog/report.json`,
`.local/logs/history-outage-100-b.log`.

Первая попытка smoke (`scheduler-load-100-mqWlWh`, `history-outage-100.log`) FAIL:
остановка была после terminal маленьких jobs, поэтому публикации больше не читались.
Исправлена точка остановки; добавлена проверка, что оба draw ещё не terminal.
Это ошибка постановки теста, не найденный обход проверки публикаций.

Большой10000-wallet:4/4 отказа остановили отправки, nonce364 и прогресс
Short13/Monthly12 неизменны; main/scheduler journals побайтно прежние.

| Сбой | Чтений tx | Время отказа, локально |
|---|---:|---:|
| tx-error | 1 | 6.71s |
| tx-null в конце обеих публикаций | 314 | 27.49s |
| logs-empty | 0 | 12.00s |
| tx-corrupt | 2 | 12.28s |

Это время полного неуспешного прохода нового процесса после подключения,
не latency одного RPC и не SLA. В каждом случае0 broadcast attempts.
Итог10000-wallet: PASS, exit0. Данные и лог:
`.local/logs/scheduler-load-10000-G1B5Uc/report.json`,
`.local/logs/history-outage-10000.log`.

- По10000 разных адресов,105000 попыток и157 порций в каждом draw.
- Здоровый новый процесс:40.40s активного прохода,322 tx reads
  (314 публикаций +8 отправленных транзакций), прогресс13/12→17/16.
- 42 прохода,327 уникальных транзакций processing/finish/claim;
 521.81s активной работы (8m42s), без четырёх fault-проходов, подготовки и sleeps.
 Публикации/seed подготовлены отдельно за53.74s; это не время полного Pons цикла.
- 11 выплат; балансы всех победителей совпали с независимыми Short/Monthly моделями.
 Vault2100→101 raw units:1999 выплачено, reserved/claimable0, остаткиfreeShort1
 иfreeCurrent100. Не долларовые суммы: тестовые минимальные units.
- Restore ранних main/scheduler файлов после выплат:29.24s с314 reads,
 следующий проход1.07s с0 reads; оба0 sends, nonce и accounting неизменны.

запускался: runtime не изменён, проверяется конкретный fault/recovery путь.

Команда:

```text
node scripts/benchmark-scheduler-load.cjs 10000 --history-outage
```

Использован сохранённый неизменённый Solidity artifact через
RH_TEST_ARTIFACT/RH_TEST_ARTIFACT_SHA256. Обычный benchmark без флага сохраняет
пробы2/8/32; fault-режим их пропускает: скорость разных лимитов здесь не исследуется.

## Порядок восстановления и границы обещания

1. Сохранить полный комплект jobs/config/journals и сообщение ошибки. Отсутствие
   calldata не означает нулевой dataset или право создать новый розыгрыш.
2. Восстановить чтение старых headers/events/transaction calldata и state на
   закреплённой высоте проверки. Наличие свежего chain head недостаточно.
3. Запустить тот же исполнитель с прежними config/state, одним signer/writer.
   Он заново проверяет публикации и получает прогресс из цепочки.
4. Сверить terminal resultHash, выплаты, nonce и оставшиеся обязательства;
   не очищать journal и не делать reroll для обхода отказа.

Разные типы истории — разные требования: getTransaction/getLogs за старые блоки
и historical eth_call/storage не взаимозаменяемы. Предыдущий отказ публичного
fork RPC по старому storage сам по себе не доказывает недоступность старых tx.
Выбранный реальный провайдер должен проверяться по нужным методам и давности.

Этот тест восстанавливает доступ к **тому же локальному узлу**, а не переключается
на независимый архив. Замена rpcUrl сейчас меняет identity основного журнала.
Нельзя обходить это ручной правкой configHash. Production failover через стабильную
точку доступа или отдельную проверяемую миграцию ещё предстоит спроектировать и
проверить; данный пакет его не реализует.

Не проверялись power loss, потеря ключей, другой хост, полный Pons watch service
и HTTP UI при таком отказе. Нулевая отправка относится к описанному сценарию двух
активных draw с недоступной историей; это не запрет обслуживать независимые,
уже подтверждённые обязательства при частичном отказе одного источника.
