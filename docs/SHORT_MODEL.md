# Локальная модель Short

Реализовано 14.09.2026 по разделам 8–9 [PRODUCT_SPEC](PRODUCT_SPEC.md). Это воспроизводимый Python-симулятор, не production controller и не проверка экономики торговли. Контракты не менялись. Нужен Python 3.10+; сторонние Python-пакеты, сеть и кошелёк не нужны.

## Запуск

```powershell
npm run test:short
npm run report:short
python scripts/short-report.py --rounds 100 --seed 20260914 --output research/short-model-report.json
python scripts/short-report.py --p-max 1/3 --h-e 4 --h-l 8 --weights 1,1,2,4 --min-prize-raw 1000000 --budget-raw 100000000
```

Последняя команда демонстрирует изменение параметров, не утверждает их. Денежные аргументы заданы в raw units: в сценариях 1 USDG = 1 000 000 units. `--output` перезаписывает только явно заданный файл; без него выводится краткая таблица. Полный отчёт содержит seed, правила, настройки сценариев и результаты. Прогон по умолчанию — 300 раундов; сохранённый пример ниже — 100.

## Что моделируется

[short_model.py](../scripts/short_model.py) содержит неизменяемые состояния и чистые переходы. Новый вызов возвращает новое состояние; при ошибке исходное остаётся прежним.

- `Rules`: версия, точный дробный p_max, h_e/h_l, целочисленные веса, минимум приза и минимум кошельков. Эти настройки экспериментальные.
- `admission`: принятая рациональная формула через Fraction; без потери точности и промежуточных float. Python integers не ограничены uint256.
- `basket`: floor(D/sumW), проверка готовности базовой единицы, положительные призы; вся пыль сохраняется.
- `freeze`: один pending, бюджет только из свободного Short, фиксированные участники/entries/usedLuck/правила. Старые попытки находятся в snapshot, новые накапливаются отдельно. Неготовность не меняет состояние.
- `settle`: независимый допуск каждого участвующего кошелька, отдельные равномерные перемешивания кандидатов и корзины, максимум один приз. Все старые short attempts расходуются; проигравшим +1 Luck, выигравшим сброс при назначении. Monthly attempts сохраняются. Следующий short — не раньше settlement + 6 часов.
- `fund`: пополняет уже выбранный SHORT, не моделирует GENERAL/creator allocation. Поступление во время pending не расширяет frozen бюджет.
- `claim`: получает накопленный долг, не влияет на Luck или календарь. Старые unpaid credits сохраняются между draws.

Участники сортируются по идентификатору до получения случайных значений: порядок входного списка не задаёт приоритет. `random.Random(seed)` нужен только для воспроизводимых экспериментов; это не безопасный RNG для денежных розыгрышей. В runner один исход на раунд, без подбора результата. Прямой API намеренно позволяет исследователю повторять frozen snapshot с разными seeds; его нельзя использовать как механизм принятия production-результата.

Проверяемое денежное равенство:

```text
custody = freeShort + pendingBudget + sum(claimable)
after freeze / settle: custody не меняется
after funding: custody растёт на funding
after claim: custody уменьшается ровно на выплаченное
```

При M<K выдаётся случайное подмножество корзины, включая возможность крупного приза. При M>K допущенные без приза тоже получают Luck. No-winner является завершённым исходом; ошибка RNG оставляет pending и не расходует попытки. Повторный/stale settlement и ранний freeze отклоняются.

## Сценарии и первый результат

[short-report.py](../scripts/short-report.py) сравнивает базовый вариант с более быстрым и медленным ростом Luck. Примеры: 3 участника, 100 обычных, 500 с высоким Luck, один крупный покупатель среди обычных, 1 000 мелких кошельков, слишком маленький бюджет и крупное внешнее пополнение.

Каждый экспериментальный раунд добавляет D в Short и новую порцию entries каждому кошельку. Это заданный приток извне, а не вычисленный комиссионный доход. D остаётся фиксированным, не растёт автоматически из накопленных остатков. Monthly attempts накапливаются без месячного розыгрыша, claims остаются неоплаченными. Идентификаторы кошельков синтетические; сценарий множества кошельков не рассчитывает прибыль их владельца.

Сохранённый [отчёт](../research/short-model-report.json): 100 раундов, seed 20260914, базовые p_max=2/5, h_e=3, h_l=6, веса [1,1,1,1,2,2,3,5], m=1 USDG, D=100 USDG. Это **не принятые настройки запуска**.

| Сценарий базового варианта | Победителей за draw, среднее | Выдано от внесённых бюджетов | Кошельков без единого выигрыша |
|---|---:|---:|---:|
| 3 участника | 0,51 | 6,7% | 0 |
| 100 обычных | 8 | 100% | 0 |
| 500 с начальным Luck=100 | 8 | 100% | 69 |
| 1 000 мелких кошельков | 8 | 100% | 433 |

При 8 призах за 100 draws есть максимум 800 назначений, поэтому среди 1 000 постоянных участников хотя бы 200 обязательно останутся без победы, даже если повторных побед вообще нет. Luck не увеличивает число мест. Наблюдаемые 433 — результат одного seed, не универсальная оценка; сравнение трёх вариантов по одному прогону не доказывает превосходства настройки.

Отчёт также показывает долю допусков, no-winner draws, остаток Short, unpaid claims, вероятность победы первого кошелька по наблюдениям, максимальную серию проигрышей и квантили завершённых ожиданий победы. Последние не включают ещё не завершившиеся ожидания: рядом обязательно смотреть never-won и максимальную наблюдаемую серию. Серия проигрышей измеряется участиями, не временем.

## Проверки и границы

[Тесты](../test/short-model.test.py) проверяют точную формулу и монотонность, нулевые entries, большие числа, rounding/readiness, изоляцию frozen, новые entries/funding во время pending, win/no-win, обновление проигравших, monthly independence, stale/double/early переходы, ошибку RNG, сохранение unpaid credits и денежного равенства на серии циклов. Положения призов проверяются также на воспроизводимом наборе seeds; это не сертификация RNG.

Модель не выбирает автоматически бюджет D, не устанавливает безопасные торговые стратегии и не доказывает отсутствие farming. Она не реализует attribution BUY, indexer, on-chain хранение, conversion, месячный random, спонсорские акции или восстановление после недоставленного RNG. Стоимость gas не измерена, точный Fraction ещё нужно перевести в заданную ограниченную арифметику для контрактов. Входные состояния создаёт исследователь; они не являются недоверенными запросами к серверу.
