# Pons: нагрузка на admitted-истории, 03.10.2026

Тестовый пакет поверх `f0d26f0`. Код исполнения индексатора/API и продуктовые правила
не менялись. Добавлен `scripts/benchmark-pons-admitted.cjs`.

## Что проверено

Synthetic curve BUY в каждом блоке, 100 кошельков. Для каждого кошелька чередуются
60/40 USDG; ожидаемые билеты и carry считаются отдельно от replay. Настоящие модули
policy admission, scanner, persistent indexer, lifecycle reducer, snapshot consumer
и API reader работают с mock RPC/runtime/policy. Это не исполнение сделок в Pons.

На каждом размере: catch-up порциями до 1000 блоков; idle; добавление одной покупки;
новый OS-процесс/restart; API; повреждение файла и восстановление backup. Для каждого
прохода проверяются число ELIGIBLE-покупок, все кошельки и отсутствие двойного начисления.
Append сканирует/replay ровно один блок; idle/restart/restore — ноль. Ledger hash
после append совпадает с restart/API/restore. API независимо подтверждает Short,
Monthly и carry всех кошельков. Повреждённый JSON даёт unavailable; копия публикуется
через rename и снова проходит indexer и независимый readSnapshot.

API-замер: cold load и 100 кошельков, 1000 тёплых чтений, 32 одновременных запроса
через настоящий worker reader с новым кэшем. Это не HTTP/network/browser нагрузка.
Резервная копия восстанавливается по прежнему пути с тем же config; чужой сервер,
диск, config recovery и денежные журналы этим не проверены.

## Ограничения

Lifecycle v1 здесь проверяет только открытые билеты. Freeze/consume, множество draws,
reward storage и public reserves не нагружались. Curve — один маршрут; self-batch,
0x и EntryPoint остаются предметом отдельного смешанного workload. Нет сетевой
задержки, реорганизации цепочки и длительного soak. Не следует называть это полным A4.
RSS включает генератор mock-цепочки и все вспомогательные проверки; в API-фазе
сосуществуют sync-reader и worker. Это не оценка памяти одного production-сервиса.
Замеры одиночные локальные, без обещаний mainnet throughput или SLA.

## Повторение

```powershell
node scripts/benchmark-pons-admitted.cjs .local/logs/NEW_DIRECTORY 100,1000,5000
node scripts/benchmark-pons-admitted.cjs .local/logs/OTHER_NEW_DIRECTORY 10000
```

Только новая директория: benchmark отказывается перезаписывать существующую.
Результаты/state/backup сохраняются там; RPC в сеть и signer отсутствуют.
В каждой директории `report.json` содержит времена, размер файла, RPC-счётчики,
ledger hashes, cache metrics и пик RSS. Сводное evidence хранится в
[evidence](evidence/PONS_ADMITTED_LOAD_2026-10-03.json).

## Решение для следующего пакета

Кэш ускоряет повторные ответы, но публикация нового снимка снова требует полного
проверочного replay. Не увеличивать freshness/read timeout ради зелёного статуса.
Следующий пакет: ограничить стоимость обновления потребителя и хранения истории
с сохранением независимой проверки, проверкой rollback и совместимого restore.
Перед изменением формата сравнить более узкий вариант incremental consumer с
сегментированным хранением. Денежные журналы и обязательства не сбрасывать.

## Результаты

Все **24 прохода** (4 размера × 6 сценариев) завершились с проверенными инвариантами.
Это адресный benchmark, не полный набор тестов проекта.

| Покупок до append | Seed, s | Idle, ms | Append, ms | Snapshot после append, MiB | API cold, ms | 32 cold worker requests, ms |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 0.54 | 114 | 117 | 0.94 | 94 | 213 |
| 1000 | 3.52 | 262 | 361 | 4.38 | 624 | 765 |
| 5000 | 19.82 | 619 | 1234 | 18.96 | 2832 | 2970 |
| 10000 | 43.02 | 1000 | 2118 | 37.18 | 5530 | 5646 |

Отдельный readSnapshot consumer: ~0.08 / 0.57 / 2.62 / 5.12s после append.
При 10000 покупок peak RSS: seed1161MiB, append806MiB, API1011MiB (границы выше).
На этой машине 10000 покупок уже дают >5s холодного API. Ошибок/таймаутов в этих
проходах нет, но считать текущую полную перезапись/replay готовой для неограниченной
истории нельзя. Freshness60s и worker timeout30s не увеличивались.
Рекомендуемый инженерный ориентир следующего сравнения: на том же workload добиться
обновления API менее1s и append менее1s; это ориентир оптимизации, не согласованный SLA.
