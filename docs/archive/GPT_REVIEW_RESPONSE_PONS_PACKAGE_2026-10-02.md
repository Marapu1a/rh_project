На плотной цепочке это увеличивает цену catch-up и поверхность отказа: недоступное историческое состояние случайного аккаунта остановит индекс, хотя известные Pons bindings/BUY можно было прочитать. Минимум: честно описать узкую границу; если хочется расширить охват, нужна проверка nonce/order с предшествующим состоянием или execution trace, а не игнорирование всех подписей. Regression: подписанная payer tuple с неподходящим nonce плюс независимый успешный type2 batch; текущий ожидаемый результат unsupported, после доказанной поддержки — eligible. ## Что просмотр действительно подтверждает

- `pons-batch-route.cjs:34–75` различает signed type4 и уже делегированный type2, для второго требует код аккаунта в parent block и консервативно закрывает same-block authorization; исполнитель закреплён адресом/hash. `pons-batch-buy.cjs` и `pons-batch-funding.cjs` требуют canonical calldata, atomic mode, ровно 2/5 calls, approvals, payer=recipient, конкретный WETH→USDG path, payment/refund/доставку TOKEN; статус диагностического shape сам по себе не даёт билетов. `pons-pool-batch-buy.cjs:9–54` требует 3/6 calls, точный Permit2/UR маршрут и согласованный USDG funding/payment; после исходной provenance проверки удаляет только unique pool→payer log из локальной проекции, а ledger сохраняет оригинальные logs и их индексы. SELL, extra calls/transfers и mixed venue не повышаются до eligible. Это доказательство для закреплённых runtime и формата, не исходник/семантика всякого будущего executor.
- `persistent-buy-indexer.cjs:44–91` оставляет canonical prefix, удаляет хвост/его cache после reorg, сканирует только suffix и связывает receipt cache с его собственным blockNumber.
