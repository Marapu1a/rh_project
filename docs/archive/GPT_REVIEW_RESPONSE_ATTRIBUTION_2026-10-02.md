# Постоянный ответ GPT — кому и когда начислять билеты

02.10.2026. Продолжение review опубликованного HEAD 2d4caa8c2d49c6656cf14dc2bc5d8565857d07a7 (код предыдущего пакета 2038a57bdb6001885c6b5b0330f991a117944699). Прочитал действующие PRODUCT_SPEC, ATTEMPT_LIFECYCLE, CUTOFF_HISTORY, PONS_CHANNEL_COVERAGE, предыдущий graduation response и raw capture конкретного EntryPoint BUY. Сверил официальные Pons V2, 0x, Uniswap v4, ERC-4337 и EIP-7702 на 02.10.2026. Новый runtime-код не проверял и тесты/RPC/fork не запускал. Это предложение политики допуска, не утверждение нового продуктового правила.

## Главное решение

**Классифицировать операции и доказательства, не возраст/тип адреса.** Человек, бот и «однодневка» на цепочке могут выглядеть одинаково. Обычный EOA может быть оператором, smart account — покупателем, EIP-7702 даёт коду исполняться по адресу EOA. «Есть код/нет кода», возраст кошелька, количество транзакций, название приложения, tx.from и Swap.sender не доказывают ни покупку, ни уникального человека. Адресный чёрный список отсекает легитимных новичков и обходится новым адресом. Исключения закреплённых hook/treasury/router/collector адресов полезны как дополнительная защита, но не заменяют анализа вызова: операторский EOA тоже способен провести служебный sweep.

В действующем PRODUCT_SPEC уже принято: без регистрации и holding, 100 накопленных nominal USDG подходящих BUY → по одной Short и Monthly entry, SELL не отменяет их; один кошелёк ограничен в одном draw, несколько кошельков одного человека — сознательный остаточный риск, KYC нет. Возрастной фильтр, обязательное удержание или «один человек = один билет» меняют эти правила; не добавлять их незаметно.

**Рекомендация MVP:** участник — экономический адрес покупки. Для обычного EOA это EOA; для ERC-4337 это исполняющий smart account (не bundler, paymaster, владелец ключа или Settler); для подтверждённого 7702 batch — делегированный адрес пользователя. Доказать, что этот адрес инициировал и оплатил одну квалифицируемую покупку в активном Pons venue и получил TOKEN на тот же адрес. Разные payer/recipient, подарки и неразделимый общий расход пока unsupported. Это консервативный выбор технического критерия; публично объявить его до активации нового route.

## Два слоя вместо «угадаем по кошельку»

1. **Широкое обнаружение.** В canonical истории искать только события curve BUY и целевого Pons pool Swap с направлением quote-in/TOKEN-out, включая транзакции через 0x, EntryPoint и неизвестные router. Сохранить candidateId и статус/причину. Не нужен trace каждого блока и не нужен Pons API как источник билетов. Другой pool с тем же TOKEN виден только дополнительной диагностикой; его допуск сейчас не следует из Pons pool event.
2. **Строгая квалификация.** По routeVersion на блоке покупки проверять pinned runtime и исполненный call path: кто платил USDG, кто получил TOKEN, целевой pool/curve и отсутствие двойного счёта, других самостоятельных BUY, несвязанных transfer/refund. ERC-20 прямой маршрут может обойтись calldata+receipt; посредники с общими балансами и несколькими op, native ETH, внутренним funding либо неоднозначным split требуют адресного trace транзакции. Если ни logs, ни доступный trace не позволяют однозначно распределить денежный поток — UNSUPPORTED/AMBIGUOUS, basis=0, причина публична. Никакого молчаливого начисления по Transfer TOKEN или HookFeeCollected.
3. **Учёт.** basis = фактический относящийся к одной покупке USDG debit адреса с её router/protocol fee минус refund этой же покупки; quote для интерфейса, maxSellAmount и pool delta не подставлять вместо basis. Если покупка сначала финансируется ETH→USDG в том же atomic batch, отдельно доказать USDG funding leg и уникальный платёж в целевой BUY, как делают нынешние фиксированные self-batches. Для exact-output считать фактическое исполнение. Если один wallet тратит 101 USDG через внешний и Pons pool, нельзя приписывать все 101 целевому leg. Делить общий fee между legs либо считать внешнюю покупку — отдельное продуктово-экономическое решение.
4. **Дедупликация.** Ключ события = (chainId, blockHash, txHash, logIndex); дополнительно закрепить экономическую ветку исполнения и её уникальные платежи. Одна плата не может стать двумя entries через вложенный batch/Settler и самостоятельный pool decoder. Несколько независимых покупок в одном tx можно признать лишь при непересекающихся доказанных payer→recipient flow и calls; иначе отклонить весь неоднозначный набор. Reorg пересобирает незамороженный canonical suffix.

## Когда появляется билет

Сначала обнаружение на блоке BUY; пользователь видит «ожидает финальности / проверки маршрута», без обещания entry. После canonical finalized покрытия и admission версии route, активной **на блоке покупки**, replay добавляет basis к carry адреса: каждые 100000000 raw USDG создают entry. Дата sweep/claim creator fee не определяет эту entry и не превращает pending TOKEN в призовые USDG. При cutoff в draw попадают только OPEN attempts из полностью включённых блоков; BUY между cutoff и FREEZE остаётся OPEN для следующего цикла. После freeze результат этого draw не пересчитывается задним числом. Новый adapter активируется на будущее после публичного объявления, а не задним числом по старым покупкам. Сайт должен различать обнаруженную покупку, подтверждённый basis/entries, unsupported с причиной, OPEN/FROZEN/CONSUMED и реально обеспеченный USDG-приз.

## Контрпримеры, которыми ломается «универсальный» shortcut

| Ситуация | Наивный ответ | Нужное решение |
| --- | --- | --- |
| Реальный Harmonic 0x BUY tx 0x764d4c88… block 78254717 | tx.from bundler, Swap.sender Settler, TOKEN у smart account 0xdb16141a… | Pool BUY и recipient доказаны, но 0.117019114351378252 ETH — input pool, а не доказанный расход account; trace op/native flow или отказ. Для QIANQI ещё нужен USDG basis |
| PRIORS 0x fork на 101 USDG | «TOKEN пришёл, значит билеты» | Маршрут прошёл через внешние v3/v4 pools, без Pons hook; 101 нельзя выдать за покупку в целевом Pons venue |
| Служебный sweep hook tx 0x4393f648… | «Есть Swap — значит чей-то BUY» | Проверять направление и call context, исключать fee-conversion/buyback. Отсутствие fee event само по себе не достаточно: комиссия может округлиться до нуля |
| Два UserOperation в одном tx | «Один tx — один покупатель» | Связать конкретный Swap, платёж и TOKEN delivery с успешной op/account по trace; failed op не получает билет |
| Первый BUY нового честного пользователя | «Молодой адрес — однодневка» | Покупку учесть при том же proof, без возраста. Боты могут заранее подготовить старые адреса |
| Купил, продал, повторил под новыми адресами | «Отсечём рабочие кошельки» | Нельзя доказать одного человека без identity. Измерять стоимость фарминга против вероятности/размера приза; принятый cap по кошельку не является cap по человеку |

## Граница реализуемой универсальности

Общее ядро: candidate → route-specific proof → wallet basis/carry → cutoff/attempts. Новую площадку или wallet implementation подключают отдельным versioned адаптером; единого безопасного decoder «любые swaps любого кошелька» нет. Переиспользовать scripts/pons-v4-buy.cjs для pool/fee/direction, pons-channel-attribution.cjs как read-only диагностику, replay-direct-buy.cjs и persistent-buy-indexer.cjs для canonical history, buy-policy-history для активации. scripts/pons-zeroex-evidence.cjs сейчас только forensic и подменяет tx.to для проверки nested trade; это **не** admission. Старые genesis и frozen commitments сохраняются.

Ближайший конкретный шаг для Codex: добыть и исполнить **EOA→AllowanceHolder→Settler→один Pons USDG pool BUY** с pinned кодом и финальными transfers, затем доказать сумму и один recipient без trace, если call graph действительно однозначен. Positive: 101 USDG, один подтверждённый basis и по одной entry Short/Monthly, carry1. Negative: SELL, другой pool, split, несовпадающие payer/recipient, дополнительный refund/fee без связи, два BUY с общим балансом → именованный отказ. Recovery: повтор индекса не удваивает запись, reorg меняет OPEN в соответствии с новой canonical веткой, старый frozen не переписывается. После этого отдельно 4337: trace конкретного tx, pinned EntryPoint/account implementation и две op разных пользователей с reverted внутренним вызовом. Если trace/RPC недоступен, ветка остаётся обнаруженной, но неподдержанной.

**Продуктовая развилка владельца на будущее:** хотим ли начислять за покупку TOKEN в любом внешнем pool даже без creator revenue Pons? Сейчас я рекомендую ограничиться доказанным Pons venue; иначе финансирование призов и обещанный охват расходятся, а общий 0x split требует нового правила распределения basis. Вопрос уникальности человека уже решён в MVP как остаточный риск; повторно маскировать его «возрастом кошелька» не стоит.
