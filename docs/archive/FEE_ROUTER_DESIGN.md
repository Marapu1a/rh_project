Статус: реализован минимальный прототип FeeRouter; локальные тесты и интеграция с реальными PAIR/Uniswap на локальном fork прошли 2026-09-11. В публичную сеть ничего не отправлялось. Это не завершённый security audit и не готовый production deployment.

## Разделение ответственности

```text
Uniswap PoolManager
  → PAIR native fee vault (collectFees)
  → FeeRouter (claim, измерение фактически полученного актива)
  → кредит фиксированному получателю по правилам кампании
  → ERC20 transfer получателю (pay)
```

FeeRouter знает только два ERC20: проектный TOKEN и quote USDG. Активы не конвертируются. Комиссия PAIR и её protocol share не пересчитываются нашим контрактом: router распределяет только полученную creator revenue. В первой политике Promo получает 100%, Investor и Treasury — 0%; последующие политики могут использовать другое распределение с суммой 10000 bps.

`PromoVaultFixture` в тестах — пустой контракт-получатель. Он позволяет проверить фактическое финансирование, но не реализует учёт призов, резервирование, claim победителей или RNG. Это следующий самостоятельный модуль.

## Принятая для прототипа граница кампаний

Рабочее допущение, вынесенное пользователю на уточнение: доход учитывается при получении/распознавании в FeeRouter, а не по времени исходного swap. Ответ на этот вопрос пока не получен; перед production freeze правило нужно подтвердить.

- `harvest` относит фактически полученные комиссии к текущей активной кампании.
- PAIR epoch и наша campaignId — разные сущности. Получение старой PAIR epoch не возвращает деньги в старую Promo campaign.
- Не полученные из PAIR комиссии могут попасть в следующую кампанию. Поэтому cadence keeper влияет на распределение дохода около границы. Контракт не доказывает полноту сбора всех комиссий к дедлайну.
- Прямые ERC20-переводы не имеют callback с датой поступления. Они учитываются при `sync`; перед сменой политики весь неучтённый баланс относится к старой кампании. Даже перевод, сделанный после окончания, но до активации следующей кампании, попадёт старой.
- После `endsAt` новые `harvest` и `sync` останавливаются до `openNextCampaign`; `pay` уже начисленных долгов продолжает работать. `collect` можно вызывать, но он оставляет деньги в PAIR vault.

Таким образом, это явная модель получения дохода с ручной активацией следующего периода, а не точная разбивка swap fees по календарным границам. Если нужна последняя, текущую модель распределения нельзя считать окончательной: потребуется сверка доходов по сделкам/позициям и отдельное решение для позднего получения.

## Инварианты и права

1. Project TOKEN и USDG фиксированы в constructor; proxy/upgrade, произвольного external call, swap и admin withdrawal нет.
2. Источник привязывается владельцем один раз после launch. Проверяются наличие кода, совпадение projectToken и единственный recipient текущей PAIR epoch: сам router с долей 10000 bps.
3. Адрес PAIR vault и positionId владелец должен сверить с launch receipt. Getter-проверки не являются доказательством происхождения произвольного контракта от PAIR; ошибочную одноразовую привязку исправить нельзя. В fork-тесте оба значения извлекаются из событий launch/NFT transfer.
4. `collect()` вызывает только фиксированный vault и positionId. `harvest(asset,pairEpoch)` принимает только два поддержанных актива и вызывает только фиксированный vault.
5. Любой keeper может запускать collect, harvest, sync и pay. Получатель выплаты берётся из его собственного сохранённого кредита; keeper не может перенаправить чужую долю себе.
6. Policy каждой открытой кампании неизменна. Новую можно открыть только владельцу после окончания старой. Старые кредиты сохраняются даже при смене адресов получателей.
7. Входящий объём определяется разницей балансов, а не возвращаемым PAIR значением. Поддерживаются обычные ERC20 с постоянным балансом между переводами: fee-on-transfer/rebasing assets не входят в контракт поддержки.
8. Выплаты независимы по активу и получателю. Revert ERC20 transfer откатывает уменьшение его кредита; другие выплаты остаются доступны. Входы, затрагивающие средства, защищены ReentrancyGuard.
9. Владение передаётся через Ownable2Step. Потеря владельца или renounceOwnership остановит открытие следующих кампаний; существующие кредиты останутся выплачиваемыми. Для реального запуска нужен управляемый admin-контракт/кошелёк и keeper, которые ещё не настроены.
10. Незнакомые токены и принудительно зачисленный ETH не маршрутизируются; rescue-функции нет. Нельзя отправлять их сюда в расчёте на возврат.

## Округление и платёжеспособность

Для каждого asset/campaign учитывается накопленный доход. Доля получателя рассчитывается как `floor(totalReceived × bps / 10000)`, новое начисление — разница с предыдущим накопленным результатом. Поэтому дробление одного поступления на множество маленьких не меняет начисленные доли.

Остаток округления хранится в router, не признаётся повторным доходом и составляет максимум 2 raw units на asset/campaign. При закрытии кампании он начисляется её PromoVault, даже если promoBps=0. Это отдельное явно заданное правило, не процентное перераспределение крупного дохода.

`accounted[asset]` = невыплаченные кредиты + резерв округления. `received[campaignId][asset]` = накопленный распознанный доход. Кредит ещё не является фактическим балансом PromoVault: финансирование состоялось только после успешного `pay`/Transfer. Будущий PromoVault должен резервировать награды исключительно по собственному балансу, не по ожидаемым комиссиям или кредиту в router.

## Локальные тесты

`npm test`: 7/7 passed.

- Оба актива, получение, кредит, выплата и защита от повторного списания; фиктивный PAIR возвращает заведомо ложную сумму claim, чтобы проверить учёт по balance delta.
- Фиксированный источник, поддержанные активы и права владельца.
- Мелкие поступления и выплаты при 70/20/10, сохранение и закрытие резерва округления.
- Переход кампании, сохранение старых кредитов и отложенный PAIR claim по новой политике.
- Ошибка transfer одному получателю не мешает остальным.
- Reentrant callback не позволяет повторно выплатить кредит.
- Невалидная политика/источник отклоняются без частичного изменения состояния.

## Воспроизведение и следующий шаг

```powershell
npm ci --ignore-scripts
npm run compile
npm test
npm run test:fork
```

Fork-тест читает публичный RPC, но все транзакции отправляет только во встроенный локальный provider. Приватные ключи и `.env` ему не нужны. Результат перезаписывается при следующем запуске; блок и суммы могут измениться. Требуется ещё не занятый vanity address из `research/native-launch-corrected.json`. Публичных deployment scripts в проекте нет.

Следующий модуль — PromoVault: фактическое финансирование → резерв под завершённый draw → обязательства перед победителями → claim без возможности потратить уже зарезервированные средства. RNG/определение победителей не должны появляться внутри FeeRouter.

Использованные первичные справочники: [OpenZeppelin access control](https://docs.openzeppelin.com/contracts/5.x/access-control), [SafeERC20](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20). В проекте закреплены точные версии пакетов и package-lock.json; PAIR интерфейс взят из исследованного frontend ABI и проверен на fork.
