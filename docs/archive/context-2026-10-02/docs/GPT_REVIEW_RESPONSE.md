## Сбой проекции и согласованность generation

Сегодня `observePublic` бросает ошибку до публикации новой generation; catch сохраняет старый `index`, но меняет общий `status.state` на `waiting` (`persistent-buy-indexer.cjs:73–86`). `readSnapshot` тогда откажет новому draw. API видит старую generation как stale или unavailable, но не обязан сообщать, что BUY ledger был успешно пересчитан в не опубликованной попытке.

Минимальная правка: после обязательных policy/BUY/lifecycle/reward проверок раздельно обработать **временный read/RPC outage публичной проекции**. Атомарно публиковать новый проверенный BUY index и явный статус `publicProjection:{state:'unavailable',head,blockHash,...}` без старых reserve/totals; `publicObservation:null` в этой generation. Index status `caughtUp/catchingUp` остаётся действительным для coordinator. API overview возвращает 503/unavailable, wallet данные могут быть observed по той же generation с явной provenance; не превращать старые totals в свежие. При восстановлении публиковать проекцию с тем же head/hash/manifest и возвращать overview только после её валидации. Ошибка code hash/binding/«reserve deficit» из `public-observation.cjs:15–24` — **не** обычный optional timeout: явно классифицировать как integrity alarm/stop новых jobs до разбора, не глотать общим catch. Не ослаблять обязательные BUY/reward ошибки.

Одна atomic rename уже даёт целый JSON (`local-scheduler-state.cjs:25–33`), но API читает с open fd и stat до/после (`user-status-api.cjs:48–70`), async worker ещё сверяет generation перед ответом (`:89–95`). При замене во время чтения нужен 503/retry, без смеси двух поколений. Для каждой успешной projection хранить привязку к `head/blockHash/manifestHash` и, при необходимости, `ledgerHash`; проверять при prepare. Два соседних HTTP ответа **не обещают** один head; клиенту показывать provenance каждого. Смена config требует остановки writer/readers, новый индекс и явного restart, а не принятия чужого checksum. Reorg: текущие tail rollback и cutoff hash revalidation сохраняются; глубже лимита или при несовпадении ветки — wait/manual. Повреждённый файл нельзя подменять старым «валидным» без проверки on-chain ветки. Checksum подтверждает целостность файла и совпадение конфигурации, **не честность RPC, полноту BUY истории или finality**.
