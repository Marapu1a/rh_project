# PAIR Promo Token — MVP Specification

> **АРХИВ.** Документ отражает прошлый этап, не текущие правила. Актуальная логика: [PRODUCT_SPEC](../PRODUCT_SPEC.md); реализация: [IMPLEMENTATION_STATUS](../IMPLEMENTATION_STATUS.md). Числа и следующие шаги ниже относятся к дате документа.


**Status:** Product freeze for MVP  
**Target network:** Robinhood Chain  
**Launch layer:** PAIR  
**Purpose:** single source of truth for us and Codex before implementation

---

# 1. Product in one sentence

> Launch a simple meme-token on PAIR where eligible BUY volume earns promotional entries, regular draws pay small rewards in TOKEN, and all monthly entries participate in a larger USDG jackpot funded from the project's creator revenue.

The user-facing product must remain simple even if implementation is not.

---

# 2. Core principles

1. **TOKEN stays simple.**
2. **Promo is separate from TOKEN.**
3. **Investment/revenue-sharing is separate from both TOKEN and Promo.**
4. **No unnecessary DeFi complexity.**
5. **Creator revenue routing must be configurable.**
6. **All economics must be transparent and reproducible.**
7. **Rules of an active promo period cannot be changed retroactively.**
8. **Build one complete working loop before adding features.**

If a new feature cannot be explained in one sentence and does not materially improve the MVP, do not add it.

---

# 3. What we are building

Three independent layers:

```text
TOKEN
  = ordinary meme-token

PROMO
  = marketing game layered on eligible TOKEN purchases

PROJECT REVENUE
  = creator fees generated by trading activity
```

Future investor infrastructure is a fourth independent layer:

```text
INVESTORS
  = separate agreements/contracts receiving a configurable share of project revenue
```

These layers must not be conflated.

---

# 4. TOKEN

TOKEN is an ordinary ERC-20 meme-token launched through PAIR.

Requirements:

- fixed supply;
- no staking;
- no wrapper token;
- no rebasing;
- no dividend rights;
- no embedded revenue-sharing rights;
- no embedded jackpot rights;
- no investor rights;
- no additional minting for rewards;
- freely tradable independently of Promo.

TOKEN must continue to function even if the Promo system is permanently disabled.

The TOKEN contract should know nothing about:

- draws;
- entries;
- jackpot;
- investors;
- creator fee allocation;
- treasury policy.

---

# 5. Launch stack

Initial launch architecture:

```text
Robinhood Chain
      ↓
     PAIR
      ↓
 Uniswap V4 market
      ↓
    TOKEN
```

PAIR is expected to provide the market/liquidity/trading layer.

We do **not** build our own DEX for MVP.

Before implementation, verify current PAIR behaviour:

- launch flow;
- supported quote assets;
- creator fee mechanics;
- fee routing capabilities;
- relevant Uniswap V4 events;
- API availability;
- whether TOKEN/USDG is practical or another quote asset is preferable.

Do not assume historical documentation is still correct. Verify first.

---

# 6. Eligible BUY volume

Only BUY volume generates promotional entries.

Initial working rule:

```text
$100 cumulative eligible BUY volume = 1 entry
```

Example:

```text
BUY $60  → 0 entries, carry = $60
BUY $50  → 1 entry, carry = $10
BUY $240 → +2 entries, carry = $50
```

Transaction splitting provides no benefit.

Number of swaps does not matter.

Only cumulative eligible BUY volume matters.

---

# 7. SELL volume

SELL transactions do not directly create promo entries.

However, SELL activity:

- returns TOKEN to the AMM pool;
- creates trading volume;
- generates fees;
- supplies TOKEN that future buyers can purchase.

A future buyer then generates eligible BUY volume and new entries.

Therefore, TOKEN rewards may naturally return to the market without requiring artificial recycling logic.

---

# 8. Eligibility

The TOKEN itself remains permissionless.

Promo participation is an **opt-in layer**.

Working flow:

```text
Connect Wallet
    ↓
Join Promotion
    ↓
confirm country / age eligibility
    ↓
accept Promo Terms
    ↓
sign wallet message
    ↓
wallet becomes promo-eligible
```

Only BUY activity from promo-eligible wallets generates entries.

This separation is intentional:

```text
TOKEN trading ≠ automatic Promo participation
```

---

# 9. Short promo draws

Short draws use:

**fixed time windows + a minimum entry threshold**

Initial working parameters:

```text
draw interval: 6 hours
minimum entries required: 30
```

Example:

```text
12:00 → 7 entries  → SKIP
18:00 → 24 entries → SKIP
00:00 → 41 entries → DRAW
```

If threshold is not reached:

- entries roll forward;
- reward budget rolls forward;
- no artificial micro-draw occurs.

If volume is extremely high:

- draw still occurs only at the scheduled window;
- no draw machine-gun every few seconds.

Parameters are configurable between promo periods.

---

# 10. Short reward probability

Initial working target:

> roughly 1 out of 3 entries wins something.

This is not yet a final probability distribution.

Design goal:

- wins should occur often enough to create emotional feedback;
- most rewards should be small;
- occasional larger short-term rewards may exist;
- short draws must not consume the monthly jackpot budget.

Exact probability and payout distribution will be modeled after actual PAIR fee mechanics are verified.

---

# 11. Short rewards are paid in TOKEN

Regular short-draw rewards should be paid in TOKEN.

Reasons:

1. creator-side trading fees may naturally accumulate TOKEN;
2. no need to constantly swap TOKEN into USDG;
3. winner can hold or sell;
4. selling naturally generates more market activity;
5. no new TOKEN supply is created.

Critical rule:

> TOKEN rewards must come only from TOKEN already owned/earned by the project or promo system.

Never mint new TOKEN for rewards.

---

# 12. Monthly Jackpot

Every eligible promo entry also participates in the current monthly jackpot.

Example UI:

```text
SEPTEMBER JACKPOT
4,827 USDG

17 days remaining
```

One eligible BUY therefore creates two layers of engagement:

```text
BUY
 ↓
entry in upcoming short draw
+
entry in monthly jackpot
```

Monthly jackpot should preferably be paid in **USDG**.

Reason:

A major prize should feel like actual money, not additional project tokens.

---

# 13. Creator revenue architecture

Creator revenue must **not** flow directly into one hard-coded use.

Use a configurable revenue routing layer.

Conceptual architecture:

```text
PAIR
  ↓
Creator Revenue
  ↓
FeeRouter
  ├── PromoVault
  ├── InvestorVault   (future)
  └── Treasury        (future)
```

Initial MVP allocation:

```text
promoBps    = 10000   // 100%
investorBps = 0
treasuryBps = 0
```

Future example:

```text
promoBps    = 7000
investorBps = 2000
treasuryBps = 1000
```

Invariant:

```text
promoBps + investorBps + treasuryBps = 10000
```

Do not hard-code 100% Promo into the architecture.

100% Promo is only the **initial policy**.

---

# 14. Revenue policy changes

Revenue policy changes must not retroactively affect an active Promo campaign.

Preferred model:

```text
Campaign / Epoch N
  → fixed revenue parameters

Campaign / Epoch N+1
  → new parameters may be applied
```

Once a campaign begins, its rules must remain immutable for that campaign.

This applies to:

- revenue allocation;
- entry threshold;
- draw interval;
- minimum entries;
- reward distribution;
- eligibility rules;
- randomness method.

---

# 15. PromoVault

PromoVault receives only the share allocated to Promo.

Its responsibilities may include:

- receiving TOKEN-side creator revenue;
- receiving USDG/quote-side creator revenue;
- funding short TOKEN rewards;
- funding monthly USDG jackpot;
- tracking available promo assets;
- preventing over-distribution.

PromoVault must not know or care about investor economics.

---

# 16. Future investor layer

Investor infrastructure is **not part of MVP implementation**, but the architecture must not prevent it.

Future model:

```text
Investor funds project
        ↓
receives agreed share of creator revenue
        ↓
until defined cap / term / agreement ends
```

Example:

```text
investment: $5,000
revenue share: X%
return cap: 1.5x
```

Investor rights must never be embedded into TOKEN.

Investor rights belong to a separate:

- agreement;
- contract;
- vault;
- accounting layer.

TOKEN holders are not investors by default.

---

# 17. Why investor rights remain separate

We want TOKEN to remain:

```text
meme + market + community
```

Not:

```text
security-like revenue participation instrument
```

Therefore:

- no automatic creator revenue for TOKEN holders;
- no project profit share embedded in TOKEN;
- no promised yield attached to holding TOKEN;
- no investor rights encoded into TOKEN metadata or token contract.

---

# 18. Preliminary fee math

Historical/current working assumption to verify before implementation:

```text
swap fee ≈ 1%
creator share ≈ 70% of collected fee
```

Illustrative only:

```text
$100 eligible BUY volume
→ ~$1 gross swap fee
→ ~$0.70 creator-side revenue
```

If:

```text
$100 BUY = 1 entry
```

then approximate creator revenue generated per entry is:

```text
~$0.70
```

These values are **not implementation constants** until current PAIR mechanics are verified.

---

# 19. Wash-trading constraint

The system must never make simple reward farming profitable.

Required relationship:

```text
fees + slippage + gas > expected promo reward from artificial volume
```

Illustrative loop:

```text
BUY $100
SELL ~$100
```

The user pays both sides of trading cost while only BUY earns entries.

This should keep naïve wash-trading negative EV.

Before launch:

- model this using real fee parameters;
- model slippage;
- model likely gas;
- test edge cases with multiple wallets.

# 21. Entries are NOT NFTs

Promo entries are accounting records, not tradeable assets.

Do not create NFT tickets for MVP.

An entry may contain:

```text
entryId
wallet
campaignId
shortDrawId
monthlyDrawId
sourceTxHash
eligibleVolumeChunk
```

Exact schema may differ, but concept stays simple.

# 22. Source of truth

Primary source of truth:

> on-chain trading events

Expected flow:

```text
PAIR / Uniswap V4 swap
        ↓
Indexer
        ↓
normalize event
        ↓
identify BUY
        ↓
calculate eligible volume
        ↓
update wallet carry
        ↓
create promo entries
```

PAIR API may be used for:

- UI;
- convenience;
- historical display;
- secondary validation.

Do not make a proprietary PAIR API the sole source of truth if the same facts are reconstructible on-chain.

---

# 23. Indexer responsibilities

Indexer MVP responsibilities:

- subscribe/read relevant chain events;
- detect TOKEN trades;
- distinguish BUY vs SELL;
- associate activity with wallet;
- determine eligible BUY value;
- prevent duplicate processing;
- persist tx/block identifiers;
- handle reorg-safe confirmation strategy;
- update cumulative carry;
- create entries.

Indexer logic must be deterministic and replayable from chain history.

---

# 24. Randomness

Draw outcome must not depend on creator discretion.

Requirements:

- publicly verifiable;
- reproducible;
- creator cannot choose winner;
- creator cannot choose favorable seed after entries are known;
- source/method documented in Promo Terms.

Select the actual randomness mechanism only after checking what is currently available on Robinhood Chain.

Do not invent a custom pseudo-random hack for mainnet.

---

# 25. Claims

Prefer claim-based rewards rather than pushing every payout automatically.

Flow:

```text
draw completed
    ↓
claimable reward recorded
    ↓
user clicks CLAIM
    ↓
reward transferred
```

Benefits:

- avoids mass transfer loops;
- avoids unnecessary gas;
- multiple rewards may accumulate;
- easier failure recovery.

---

# 26. Promo accounting

Promo accounting must expose at minimum:

```text
current TOKEN reward inventory
current USDG jackpot balance
allocated but unclaimed TOKEN
allocated but unclaimed USDG
available unallocated balance
```

Never distribute more than the PromoVault actually owns.

# 29. Legal structure — working model

Intended conceptual separation:

```text
TOKEN
= independently tradable meme-token

PROMO
= temporary marketing campaign

CREATOR REVENUE
= revenue belonging to the project

PROMO FUNDING
= project chooses to spend part of its own revenue on promotion
```

Do not describe the jackpot as:

```text
players pool their stakes and winner takes their money
```

Working business interpretation:

> PAIR generates creator revenue belonging to the project. The project allocates part of its own revenue to promotional rewards.

This must still be validated for the actual launch jurisdiction.

Why it is interesting:

- trade promotion structures exist;
- purchase-linked promotional draws exist under certain conditions;
- meme-token treatment may be materially simpler than embedding revenue rights.

Other jurisdictions previously considered:

- New Zealand;

Not preferred for MVP:

- UK;

- Malta.

No company formation or expensive licensing is required **before the hypothesis is worth validating**.

Legal work should scale with traction.

# 31. Legal risk scaling

Initial project size:

```text
~$300–500 experimental capital
```

Working risk ladder:

```text
tiny MVP
→ basic Terms + eligibility + jurisdiction rules

meaningful volume / prizes
→ specialist crypto/promotions lawyer review

real traction
→ company + accounting + formal compliance
```

Do not ignore law.

Also do not build a multinational compliance department for a token that may die in seven days.

# 32. Abuse cases

## Transaction splitting
No advantage because entries depend on cumulative BUY volume.

## Sybil / multiple wallets
Must not create extra EV merely by splitting one person's volume across wallets.

## Wash trading
Must remain negative EV.

## Duplicate event processing
Indexer must be idempotent.

## Chain reorgs
Do not finalize entries too early.

## Randomness manipulation
Creator must not control draw result.

## Retroactive rule changes
Forbidden for active campaign.

## Reward insolvency
Draw logic must use only actual available reward inventory.

# 40. Non-negotiable separation

Key architecture rule:

```text
TOKEN         ≠ Promo
Promo         ≠ Investor rights
Investor      ≠ TOKEN holder
Creator fees  ≠ hard-coded reward stream
```

The project should be able to:

- stop Promo;
- replace Promo;
- change future Promo rules;
- add Treasury;
- add investors;
- change future revenue allocation;

without redeploying or fundamentally changing TOKEN.

# 41. Note for Codex

Treat this file as **product and architectural context**, not as permission to implement everything at once.

When receiving a task:

- work only on the requested module;
- preserve the separations defined above;
- do not invent APIs, contracts, events, or PAIR behaviour;
- verify uncertain external behaviour first;
- prefer simple, explicit code over generic frameworks;
- avoid speculative abstractions;
- do not add features not required by the current task;
- preserve replayability and auditability where on-chain accounting is involved.

If implementation facts conflict with this document:

1. report the conflict;
2. explain the smallest required change;
3. do not silently redesign the product.
