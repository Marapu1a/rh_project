## Решение для ближайшей реализации

**Реальный 0x BUY через Pons pool подтверждён; покупатель и его фактический расход для EntryPoint пока не доказаны полностью.** Receipt подтверждает pool, направление, TOKEN delivery и успешный UserOperation, но native ETH funding не оставляет ERC-20 Transfer. Верхний отправитель — bundler, Swap.sender — Settler. Для этого случая нужен ограниченный **trace одной конкретной транзакции** плюс pinned decoder EntryPoint/account/Settler либо отказ в допуске. Для будущего QIANQI с USDG этот Harmonic ETH пример демонстрирует оболочку, но не тестирует USDG basis.

Первым кандидатом на новый versioned adapter считаю **EOA → AllowanceHolder → pinned Settler → один целевой USDG/Pons pool → тот же EOA**, без внешнего split, нативной оплаты и дополнительных покупок. В нынешней выборке из ленты Pons нет подтверждённого именно такого EOA BUY: AllowanceHolder/Harmonic 0xd3f689… и PRIORS 0x6a272f… здесь SELL. До реализации получить исполненный BUY на локальном fork и exact receipt. Прямой Universal Router и подтверждённый self-batch уже поддержаны. Внешний pool и произвольный EntryPoint не становятся eligible от узнаваемого TOKEN.

## Минимальный proof и сумма

1. Canonical block/receipt/log identity, успешная отправка, активная именно для этого блока versioned policy, pinned factory→poolId/hook/manager и runtime посредников. Выделить все целевые Swap с направлением quote-in / TOKEN-out; служебный swap hook при sweep исключить по call context, не только по отсутствию HookFeeCollected (fee может округлиться до нуля).
2. Для первого EOA AllowanceHolder профиля разобрать **реально исполненный** набор действий конкретного deployed Settler; доказать forwarded taker и конечный recipient равными одному EOA, один целевой USDG pool swap, отсутствие иной покупки, чужих transfer/refund и дополнительного route. Сопоставить USDG Transfer из wallet, оплату целевого swap, отдельные protocol/router fees и **все** USDG refunds wallet в той же связанной ветке. Для exact-output maxSellAmount есть потолок, расход определяет исполнение; для partial fill — фактические платежи и возврат, не quote. TOKEN hook fee уменьшает выход TOKEN и сам по себе не уменьшает USDG расход. ERC-20 события одного tx недостаточны при нескольких независимых BUY; нужна граница исполнения или fail closed.
3. База по принятому PRODUCT_SPEC — доказанный wallet USDG debit, относящийся к одной экономической покупке, **включая её комиссии и за вычетом её refund**. Pool quote delta полезна для проверки согласованности, но может быть меньше на router fee. Для split целевой+внешний pool нельзя по одному общему debit приписать все 101 USDG только Pons leg; даже распределение общей fee по legs стало бы новым правилом. Пока отвергать split. Если владелец решит платить билетами за **любую** покупку TOKEN вне Pons, это новая продуктовая граница и отдельный источник атрибуции/экономики, не технический флаг.
4. Нормализованный proof: chainId, policyVersion, blockNumber/hash, txHash, candidateLogIndex, venuePoolId, routeId, payer=recipient, currency=USDG, walletDebitRaw, feeRaw, refundRaw, basisRaw, перечень использованных logIndex, optional callPath/userOpHash только после доказанного соответствия. Ключ конкретного кандидата (chainId, blockHash, txHash, logIndex); экономический ключ (txHash, verified execution branch) запрещает дважды зачесть одну оплату через curve/pool и вложенный route. При reorg пересобрать canonical suffix; frozen обязательства не переписывать. Любая неразрешимая общая transfer/refund сумма — отказ.

В коде переиспользуются scripts/pons-v4-buy.cjs (pool key, signed deltas, fee, семантика direct), pons-channel-attribution.cjs (диагностика provenance), pons-zeroex-evidence.cjs (оффлайн forensic, **не admission**), replay-direct-buy.cjs (receipt/canonical scan), buy-policy-history/indexer (версионирование и reorg). Добавить отдельный явно versioned adapter в pons-profiles.cjs и dependency/runtime pins; не подменять v1/v2 decoder, не менять старые genesis. Текущий pons-v4-buy.cjs требует tx.to=Universal Router, один manager Swap и платеж USDG payer→manager: 0x Settler туда корректно не проходит. pons-pool-batch-buy.cjs допускает только точный self-batch3/6 calls. Нельзя обойти их подстановкой tx.to или receipt.logs, как диагностический decoder делает в исследовательском режиме: для реального допуска нужен свой execution proof.

## Findings, ограничения сбора и очередь

1. **Блокер автоматического 4337 начисления, confirmed по capture** — graduation evidence tx 0x764d4c88…: receipt не атрибутирует native funding/account при tx.from=bundler. Исправление: scoped trace + pinned account implementation и соответствие UserOperation; регрессия: две op разных accounts в одном tx, BUY только одной, вторая reverted/без TOKEN — один proof или отказ, никаких билетов bundler/второму account.
2. **Высокий риск завышения, confirmed для PRIORS fork** — PONS_ZEROEX_EXECUTION.md, 0x split расходовал 101 USDG, но целевого Pons pool Swap не было; 42.745140 USDG пошли по v3/v3, 58.103360 — в другой v4 pool без hook, отдельная 0.1515 USDG fee. Любой decoder «купил TOKEN/имеет Transfer → 101 USDG билетов» ошибочен. Проверка: split даёт UNSUPPORTED_ROUTE и ноль билетов, direct подтверждённый путь остаётся eligible. Частота split в общем обороте неизвестна.
3. **Доступность денег, подтверждено docs + ограничено source capture** — [Pons V2 docs](https://docs.ponsfamily.com/v2) говорят: curve.sweepFees/hook.sweepPoolFees вызывают operator либо creator; при internal conversion/buyback creator получает InternalSwapRequiresOperator. Escrow claim/claimToken снимает **уже начисленный** баланс и не конвертирует pending TOKEN. Изменение creatorFeeRecipient направляет будущие начисления и не переносит старые. В сохранённом evidence успешный ETH claim Harmonic: tx 0x6ef2d93e88dee5932657815f53b0bbd7cb13869f1136682f163d134ea92b14b3, block 78253677, 0.284206919559006064 ETH; это не доказательство будущей доступности operator. Отдельный claim-to или публичный bypass permission из прочитанных source/docs **не подтверждён**. Сценарий: quote-only sweep creator проходит, TOKEN conversion ждёт operator, старый credit payable после смены recipient. Проверить адреса/policy QIANQI при развёртывании; pending TOKEN не считать призовым USDG.
4. **Семантика fees, подтверждено для Harmonic, не для QIANQI** — graduation evidence: hookFeeBps=100, protocolFeeShareBps=3000, creatorTaxBps=0, buybackEnabled=false; creator получает остаток base fee, свой агент buy/burn — иная система. Нельзя выводить из этого 3% итогового QIANQI дохода либо обещать встроенную конвертацию на фиксированном сроке. Проверка будущего launch: зафиксировать creator tax=300 bps, base fee share, recipients, fee currency и фактически полученные USDG перед 90/5/5.
