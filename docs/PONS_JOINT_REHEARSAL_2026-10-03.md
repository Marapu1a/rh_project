# Совместный Pons BUY/index/API/draw rehearsal

Дата: 03.10.2026. Статус: **PASS на локальном fork через сохранённый Alchemy RPC**.
Первоначальные неуспешные попытки сохранены ниже как история, не текущий блокер.

## Что проверяем

`pons-collector-fork.cjs --joint-load` расширяет существующий restore drill:
128 дополнительных тестовых кошельков покупают по 60+40+1 USDG через настоящий
pinned Universal Router/Permit2 и созданный на fork Pons pool. Вместе с исходным
покупателем ожидаются 129 участников каждого draw. Четыре дополнительных кошелька
покупают ещё по 99 USDG после freeze. Для них ожидается по одному OPEN билету
каждого вида и нулевой carry; для остальных — OPEN0 и carry1 USDG. Для всех новых
кошельков ожидается по одному использованному билету каждого вида.

Сохраняются проверки реального Pons automation, persistent index, drand BLS,
денежных инвариантов vault, idle и восстановления старых файлов после выплат
без повторных отправок. API сверяется для каждого кошелька; дополнительно —
16 параллельных HTTP запросов, stale с сохранением известных балансов и
недоступный файл с HTTP503/balances=null. BUY ledger пересчитывается независимо
от сохранённого checkpoint.

## Допущения и границы

- Только локальный Hardhat fork; внешние RPC доступны через read-only proxy.
- Impersonated кошельки, синтетические ETH/USDG, тестовое `minOut=1`.
  Это не рекомендуемая настройка slippage для пользователя.
- Сохраняются прежние тестовые часы, local ArbSys, управляемая finality,
  явное донорское пополнение и локальная роль Pons conversion operator.
- Прямые curve/pool покупки; не совместная нагрузка self-batch/0x/EntryPoint.
- Это репрезентативная связка компонентов, не замер mainnet TPS и не проверка
  production deployment, внешнего оператора или независимого RPC failover.

Используем уже сохранённый Alchemy RPC из `.local/rpc-url.txt`; URL с ключом

smoke на 4..128 дополнительных кошельках; default128.

## Внешние сбои при подготовке

Краткие ошибки, якоря и SHA-256 локальных логов сохранены в
[evidence](evidence/PONS_JOINT_BLOCKED_2026-10-03.json).

1. `pons-joint-128.json`: официальный RPC не предоставил historical state для
   `eth_getProof`; сценарий не начался.
2. `pons-joint-128-b.log`: Blockreq public подготовил fork79052653, но при
   дальнейших storage reads отказал: доступно лишь последнее окно1024 блоков.
   EDR завершился с ошибкой. Это не успешная проверка сценария.
3. `pons-joint-128-c.log`: официальный RPC сначала успешно отдал fresh historical
   proofs/storage. Повтор на fork79054476 дошёл до graduation, затем не отдал
   исторический storage PoolManager `0x8366a39cc670b4001a1121b8f6a443a643e40951`:
   `historical state 10c968c8d0e582c5c074ad1a65863a9669ea151e7e72b0b2b12cc70d8fad4250 is not available`.
   EDR завершился с ошибкой. Массовые покупки и новые assertions ещё не исполнены.

На момент первых трёх попыток были пройдены только синтаксические проверки.
Сквозной результат подтверждён последующим Alchemy-прогоном ниже.

Длинный fork требует доступной истории состояния. Успешный локальный restore
не доказывает архивную доступность внешнего RPC. Не подменять отсутствующее
состояние нулями и не снимать проверки ради прохождения стенда.

## Повтор через сохранённый Alchemy

Первый запуск `pons-joint-128-alchemy.json`, fork79066665: все128 кошельков
выполнили384 покупки, индекс догнал цепочку, публикация обоих наборов началась.
Стенд завершился с `Short not frozen`: прежние16 проходов рассчитаны на малую
историю и не покрыли догоняющее индексирование плюс публикацию. Это ошибка
бюджета ожидания теста, не подтверждённая ошибка runtime.

Только для `--joint-load` граница ожидания увеличена до48 проходов; при restore
стенд также ждёт догоняющего индекса (не более48 проходов, минимум2). В каждом
restore-проходе по-прежнему запрещены отправки. Боевые лимиты, batch size100,
продуктовые правила и проверки готовности не менялись.

## Подтверждённый результат

`pons-joint-128-alchemy-b.json`: `PONS_INDEXED_AUTOMATION_PASSED`, exit0,
fork79076335. [Evidence, хеши исходников и локальных отчётов](evidence/PONS_JOINT_REHEARSAL_2026-10-03.json).
Проверено дерево поверх751563f с изменённым бюджетом ожидания тестового harness.
Runtime приложения/контрактов не менялся; полный test suite не запускался.

- 396 ELIGIBLE BUY: исходные8 +384 новых +4 поздних;129 кошельков.
- По129 участников и214 использованных билетов в каждом draw; по3 публикации
  набора. После поздних покупок осталось по5 OPEN для будущих draw.
- 11 назначенных наград выплачены: суммарно774.622900 тестовых USDG.
  Сумма событий выплат независимо сверена с уменьшением баланса vault.
- Vault874.622903 →100.000003 USDG; reserved0/claimable0,
  остатки freeShort0.000003 и freeCurrent100.
- 37 проходов автоматики, включая ожидание индексатора, остановку после proof,
  idle и5 проходов восстановления. Restore старых файлов после выплат:0 отправок,
  nonce228 и баланс не изменились; wallets/draws совпали с полным replay.
- Для каждого нового кошелька проверены использованные/OPEN билеты, carry,
  число покупок, оплаченные награды; исходный кошелёк проверен прежним API verifier.
- 16 параллельных HTTP запросов PASS; stale сохраняет балансы, отсутствующий
  snapshot даёт503 и balances=null. Файл после проверки восстановлен без изменений.
- Alchemy proxy:1783 read requests,0 retries,0 errors. Это факт одного прогона,
  не гарантия доступности произвольной глубины истории или failover.

Подготовка384 покупок заняла262.65s; проверка128 кошельков через cached reader
около1.20s. Это последовательный локальный fork и финальная API-проверка:
не live HTTP-нагрузка одновременно с покупками, не TPS или capacity benchmark.
