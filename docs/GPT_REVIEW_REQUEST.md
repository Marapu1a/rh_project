## Зачем вообще промо

Основной продукт по замыслу владельца — мем-токен с отдельной добровольной промо
надстройкой. Short и Monthly поддерживают интерес, а сайт становится местом,
куда участники приходят посмотреть розыгрыши и получить награды. В перспективе
на сайте могут появиться игры, новости, магазин и другие продукты; сейчас это
идеи, не реализованные функции или обещание roadmap.

Цель промо — в том числе привлекать покупателей токена на сайт. Поэтому полезно
распознавать покупки из разных интерфейсов, но НЕ ценой угадывания участника,
открытия фарминга или попытки охватить все возможные источники TOKEN.
Решение владельца: сомнительные случаи лучше НЕ засчитывать. При этом условия
участия, поддержка маршрутов и причины отказа должны быть честными и понятными.
Не обещаем всем держателям билеты. Welcome/holdings bonus ранее отклонён.

«Не лотерея, а мем-токен с промо» — описание намерения владельца, НЕ установленная
юридическая квалификация. Владелец предполагает, что продвижение сайта с разными
функциями может иметь значение для российского рынка. Не принимайте это за
юридическое заключение и не предлагайте маскировать продвижение токена названием
сайта. Если анализируете РФ, отдельно проверяйте актуальные первичные источники,
дату, фактическую механику, условия приобретения/участия и содержание рекламы;
обозначьте вопросы профильному юристу. География запуска сейчас не утверждается.
Юридическую ветку отделите от ближайшего технического решения.

ликвидность конкретного токена или популярность конкретного маршрута.

## Предложение, которое обсуждаем

Начинать с движений НАШЕГО TOKEN, а не собирать все исходные активы и сайты:

TOKEN Transfer → candidate transaction → подтверждённый Swap разрешённого пула
→ доказанная оплата/доставка → participant → однократный зачёт объёма.

Transfer — только обнаружение кандидата. Пересылка между кошельками, mint,
вывод LP, bridge arrival и prize claim сами по себе не дают билетов.
Для V4 адрес PoolManager недостаточен: менеджер общий, нужен pool id.
Список известных посредников помогает выбрать проверенный decoder, но правило
«последний неизвестный адрес — человек» отвергаем. Smart wallet может быть
пользователем; tx.from — relayer/solver. Не считаем каждый hop новым BUY.

Возможная альтернатива для сравнения: начинать сразу со Swap наших пулов и
использовать TOKEN Transfers для attribution. Не привязывайтесь к предложенной
очерёдности, если второй вариант проще, дешевле и надёжнее.

## Конкретные вопросы

1. Какой из этих способов обнаружения лучше для нашего deployment? Что TOKEN-first
   реально упрощает, а что всё равно требует route-specific decoding? Предложите
   минимальную архитектуру, без универсального графового движка «на все случаи».
2. Можно ли безопасно покрывать несколько маршрутов общим settlement rule?
   Где calldata/параметры ордера обязательны и где receipts достаточно? Дайте
   контрпримеры ложного зачёта, в том числе смешанные средства и batch swaps.
3. Как определять участника при payer≠recipient? Сейчас такие покупки отклоняются.
   Не меняйте правило молча: сравните оставить ограничение против отдельного
   правила для подтверждённых smart wallets/relayers. Регистрация обязательна.
4. Как отделить важные обычные покупки от бесконечного хвоста wrappers?
   Предложите 2–3 приоритетных семейства и проверяемые критерии их допуска.
   Наличие бренда/публичного адреса само по себе не доказательство безопасности.
5. Для asset→USDG→TOKEN: достаточно ли actual USDG последнего разрешённого пула?
   Для USDG→asset→TOKEN: как определить относящийся объём с refunds/split/fees?
   Для маршрута без USDG предложите границу MVP, не добавляя оракул незаметно.
6. Как показывать пользователю «начислено / покупка не соответствует условиям /
   ещё проверяется / маршрут не поддержан» без обещания задним числом начислить
   билеты и без ложного заявления, что любой Transfer — покупка?
7. Как совместить новые adapters с исправлением arbitrary JSON policy source,
   чтобы не зацементировать два route id навсегда? Нужны будущая активация,
   неизменность старых/frozen datasets и отсутствие silent trust bypass.
8. Предложите один законченный следующий implementation пакет и небольшой набор
   негативных/позитивных vectors. Не требуем поддержки всех интерфейсов до релиза.
