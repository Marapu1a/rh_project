## Что согласовали для Short

Короткий draw использует **выделенный бюджет D**, а не весь Short Reserve. Мы готовы раздать весь D; не требуется случайно удерживать его часть. При недостатке победителей остаток естественно сохраняется.

До random задаётся обеспеченная корзина: конкретное число маленьких/средних/крупных ненулевых USDG-призов, сумма ≤ D. Состав пока не выбран. «Колесо с секторами» — только человеческая аналогия, не требование к реализации или визуализации.

Процесс:

```text
проверка готовности
→ фиксация D, корзины, участников, entries, usedLuck, rulesVersion
→ случайный допуск кошельков с учётом entries и Luck
→ случайная перестановка прошедших кошельков
→ случайная перестановка корзины
→ сопоставление: один кошелёк — максимум один приз
→ фиксированный список winners и сумм
→ finalize в vault, обновление attempts/Luck
→ claim уже назначенного долга
```

Если корзина содержит K призов, а допущены M кошельков, winners = min(K,M). При M>K оставшиеся кандидаты не выиграли; при M<K невыданные суммы остаются в Short. При M=0 нет победителей. Никаких повторных жеребьёвок, чтобы обязательно заполнить корзину.

Порядок не зависит от tx sender, скорости запроса или Claim. Дополнительный вес за Luck/entries при распределении призов не применяется: они уже повлияли на допуск.

Это **заменяет** предыдущие варианты SpendFactor + нормализованные веса и генерацию суммы для каждого кандидата с проверкой остатка.

## Luck

- Участвовавший кошелёк, которому при terminal short не назначен ни один ненулевой приз: Luck += 1.
- Включая не прошедших допуск и допущенных, которым не хватило мест в корзине.
- Любой назначенный ненулевой short-приз: Luck = 0, независимо от размера и момента Claim.
- Пропуск, pending/недоставка random, отсутствие участия: изменений нет.
- Один draw даёт максимум +1, независимо от количества entries.
- Luck автоматически применяется, не сгорает от времени, не переводится и не расходуется вручную.
- Luck не является билетом: при e=0 участия нет.
- На размер приза не влияет; на ожидаемую выплату через повышение допуска влиять может.
- Monthly не получает Luck-бонус и не сбрасывает shortLuck.

Cap действует на кошелёк за один draw. Sybil-риск принят, победа каждого когда-нибудь не обещается.

## Кандидаты формулы — пока не выбраны

Codex предлагает простую рациональную форму:

```text
q(e,L) = p_max × (e + L)/(e + L + h), e>0
q(0,L)=0
```

Это приравнивает один Luck к одному дополнительному entry **только внутри допуска**. Такая эквивалентность ещё не утверждена.

GPT ранее предложил:

```text
q_base(e)=p_max×e/(e+h)
q(e,L)=p_max−(p_max−q_base(e))×r^L
```

При e=0 также нужен запрет участия. Ни p_max/h/r, ни cap самого счётчика Luck не выбраны. Сравни варианты без усложнения будущими points/NFT/manual activation.

## Минимальная state-модель — предложение

- Текущий shortLuck кошелька как доступное проверяемое состояние.
- Snapshot конкретного draw: entries, usedLuck, rulesVersion, basket/budget и фиксированный набор участников.
- Terminal результат: назначенные суммы и ровно одно применение Luck/attempts updates.
- Snapshot не меняется из-за последующих BUY или результата другого draw.

Предпочтительный по простоте кандидат concurrency: **один pending short на систему**; новые attempts копятся для следующего, пропущенные checkpoints не образуют очередь. Следующий freeze после terminal settlement и завершения обновления Luck. Это предложение, не окончательное решение владельца. Задержанный RNG останавливает новые short; monthly, funding и claims должны оставаться независимыми.

Не хотим per-wallet очереди и двойное использование одной истории Luck в нескольких pending draws. Данные прошлого результата полезно сохранять для проверки, но никакой обещанной бесшовной совместимости с будущим bankable Luck пока нет.

## Как это видит пользователь

До участия: короткие попытки, Luck, понятное объяснение потолка/допуска, корзина текущего draw после фиксации. q — **вероятность допуска, не точная вероятность получить деньги**. При дефиците корзины проходит дополнительный случайный отбор.

После результата только два денежных исхода:

```text
выигрыш X USDG назначен → Luck сброшен → приз можно получить
нет выигрыша → Luck увеличен → месячная попытка сохранена
```

Не сообщаем «вы победили» при промежуточном допуске. Не показываем нулевые призы. Не предлагаем срочно купить, чтобы Luck не сгорел: сгорания нет. Колесо/анимация не определяет outcome и не имитирует другие вероятности.

## Где ждём критики

1. Докажи/проверь cap: prize требует admission, значит P(prize_i)≤q_i≤p_max. Для K призов при условии допуска i и M_other других прошедших второй шанс равен min(1,K/(1+M_other)); полная вероятность требует усреднения по остальным. Не подставляй наблюдаемое число кандидатов как заранее известный точный шанс.
2. При многом Luck и фиксированном K растёт конкуренция. Как объяснить это без обещания, что личный итоговый шанс всегда растёт от draw к draw? Может ли насыщение Luck сделать entries практически незначимыми?
3. Предложи **один простой способ построить корзину из D**: положительные размеры, bounded сумма, малый бюджет и rounding. Никаких произвольных «идеальных» процентов: примеры обозначай примерами. Укажи смысл random permutation корзины при M<K — среди выданного поднабора может оказаться крупный приз.
4. Оцени стратегию «накопить Luck малыми участиями, потом прийти в богатый draw» в рамках принятого Sybil-риска. Не превращай задачу в полное исключение farming; отдели реальный конфликт с обещаниями от допустимой стратегии.
5. Полный сброс за любой ненулевой выигрыш — принятый простой вариант. Если видишь проблему крошечного приза, привяжи её к минимальному размеру корзины, а не автоматически вводи partial reset.
6. Может ли один pending short быть достаточным MVP? Как обрабатывать задержку результата и новые attempts без replay checkpoints и без новых per-wallet очередей?
7. Все проигравшие требуют Luck update, а не только winners. Как избежать неограниченной по gas финализации и частичного применения результата? При каких размерах данных нужна другая техника, а что можно оставить простым? Не выбирать Merkle/batching без оценки необходимости; фиксированный hash не доказывает корректность его содержимого.
8. Если vault.finalize прошёл, а внешний учёт Luck ещё нет, как исключить повторное начисление/сброс и преждевременный следующий freeze? Раздели логическую terminal outcome, запись призов и завершённое применение состояния, не создавая лишних состояний без причины.
9. Какие старые предположения надо убрать из документов/плана? Сейчас не нужны guaranteed reward для каждого admitted, обязательные 1/3 winning entries, отдельный SpendFactor, ручной банк Luck и cap на человека.

## Сценарии

| Вход | Ожидаемая семантика |
|---|---|
| Нет entries, но Luck высокий | Нет участия и изменений Luck |
| Draw skipped/pending | Не теряются attempts и Luck |
| K=10, M=30 | 10 случайных winners, прочие участвовавшие без приза получают +1 Luck |
| K=10, M=3 | Три случайных приза из корзины, остальные деньги остаются |
| Никто не допущен | Пустой draw; участвовавшие attempts использованы и Luck +1 |
| Один кандидат и большая корзина | Не больше одного случайного приза, cap допуска сохраняется |
| Prize назначен, Claim через месяц | Luck сброшен при назначении, повторного изменения на Claim нет |
| RNG задержан, наступили новые checkpoints | Нет повторного выбора, новая активность не меняет snapshot |
| Очень много проигравших | Проверяемая однократная обработка Luck без блокировки исполнения |
