# Ожидание газа и эксплуатационный статус

28.09.2026. Дополнение к [ETH refill](PROMO_NATIVE_REFILL.md).
Не пытаемся угадать будущую цену газа или постоянно поддерживать фиксированный баланс.
Дорогой gas → ожидание; нехватка ETH → ограниченный refill; source пуст/лимит → ожидание.
Watch повторяет ограниченный проход с прежним journal и продолжает при улучшении условий.
Frozen/claimable не тратятся на эксплуатацию; reroll/reset и сброс обязательств отсутствуют.

## Согласованные бюджетные проверки

`prepareRuntime` после проверки форматов отклоняет профиль, если:

- `ops.nativeFloor < fundingJob.nativeFloor` или `< deliveryJob.nativeFloor`;
- общий gas bound для pull/pay/prove/deliver меньше соответствующего child bound.

Иначе общий guard мог считать ETH достаточным, а child бесконечно возвращать
nativeFunding. Проверка включает bound до estimate, когда child ещё использует свой
конфигурационный предел. После estimate оба проверяют actual gasLimit. Разные потолки
цены gas допустимы: отправка должна пройти обе проверки; больший потолок не обходит меньший.
Нет автоматической подмены конфигурации или обнуления spending history.

Прогноз перед новым freeze остаётся консервативным предохранителем. Старый draw/claim
проверяется по стоимости текущего действия и может идти частями. Refill целится сначала
в старые обязательства, но частичный перевод не требует накопить весь прогноз для
разрешения отдельного старого действия. Это прежняя модель, не новая гарантия цены газа.

## Наблюдение и события

Оба automation CLI подключают `observePromoStatus` к `runWatch`.
Рядом с `STATE` хранится **`STATE.status`**: только наблюдение и последние32 перехода.
Файл использует существующий checksum/atomic save/lock helper; он НЕ денежный журнал,
не источник разрешений на отправку и не заменяет main/funding/RNG/scheduler state.

JSON отчёт получает `operational`:

- `state`: waiting, attention или clear;
- `reasons`: стабильный отсортированный набор причин;
- `resumeWhen`: понятные условия продолжения;
- `event`: только при изменении состояния/причин, с id, sequence и временем.

Первое проблемное наблюдение даёт waiting/attention, смена проблемы — changed,
исчезновение наблюдаемых проблем — recovered. Повторный pass и новый OS process
не создают одинаковое событие заново. Обычное ожидание расписания/seed не считается
поломкой. Clear означает отсутствие распознанной эксплуатационной проблемы в этом
проходе, НЕ завершение всех розыгрышей, наличие денег навсегда или readiness релиза.
Остановка процесса не объявляется восстановлением.

| Причина | Условие продолжения |
|---|---|
| expensiveGas | Цена gas ниже применимых потолков |
| executorNeedsETH | Достаточный bounded refill или внешнее пополнение executor |
| sourceNeedsETH | ETH внесён на отдельный эксплуатационный source |
| refillPeriodLimit | Открылось следующее окно расходов |
| refillCooldown | Истекла пауза после предыдущей подтверждённой попытки |
| refillAttemptLimit | Настроенный cap должен покрывать хотя бы газ перевода; нужна проверка профиля |
| rpcUnavailable | RPC снова отвечает; watch использует существующий bounded backoff |
| receiptPending | Сверка ТОГО ЖЕ известного hash, без повторной отправки |
| reconciliationRequired | Проверка неизвестной/несогласованной отправки оператором |

`refillBudget` сохраняется в API, но получает `constraint`:
sourceBalance / periodCap / attemptCap. Информативная причина заменяет дублирующее
executorNeedsETH в наблюдении. При нескольких проблемах сохраняется набор причин;
успех одной lane не объявляет восстановлением оставшийся RPC/source сбой.

Журнал пишется до выдачи события в JSON. Внешней доставки (Telegram/email/webhook)
нет: канал не выбран. Процесс может упасть между save и stdout; потребитель может
считать сохранённые события и дедуплицировать по id. Это bounded history, не очередь
с гарантией доставки всех уведомлений: старше32 событий вытесняются. Обычные JSON
статусы watch продолжают выходить каждый проход; уведомлять следует по `event`,
а не по каждой строке журнала.

Ошибка записи/lock status-файла даёт `statusObservationError`, не меняет результат
денежного прохода и не разрешает повторить unknown send. Денежные ошибки хранения
по-прежнему фатальны. Автоматическое удаление locks отсутствует. У нового runtime
после handoff собственная история наблюдения; денежная история переносится прежним
handoff, статус не участвует в его разрешениях.

RPC-discovery signer в Robinhood rehearsal перенесён внутрь watch-pass: временная
недоступность на старте теперь тоже проходит штатный retry/наблюдение. Inspect
по-прежнему не создаёт подписывающий signer. Ошибки парсинга/несовместимой конфигурации
остаются явной ошибкой запуска, а не бесконечным автоматическим retry.
