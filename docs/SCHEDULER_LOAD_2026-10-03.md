# Совместный большой прогон scheduler

03.10.2026, стенд поверх `cc8510f`. Runtime проекта не меняется этим пакетом.
Новый инструмент — `scripts/benchmark-scheduler-load.cjs`.

## Контур и границы

По 10 000 уникальных адресов в Short и Monthly, один и тот же набор адресов.
Всего по 105 000 синтетических попыток каждого вида, по157 chunks64. Адреса
получены из детерминированного keccak и отсортированы; это полноценные20-byte
значения, а не последовательные малые числа с преимущественно нулевыми bytes.

Вызываются реальные общие `runScheduler`, Short/Monthly executors,
`pons-transaction-journal` и `pons-gas-budget`. LocalShortController,
LocalMonthlyController, vault и ERC20 исполняются в Hardhat31337. Scheduler
загружает файл с checksum на каждом проходе; journal отправок сохраняет реальные
intents/receipts. Лимит8, maxTicks16, два вида draw обрабатываются вместе.

**Это не большой вызов `runPonsAutomation`.** Его внешние funding/RNG/claims-scan
и проверки Robinhood fork здесь не исполняются. Pons outer loop проверен
[отдельным малым fork-прогоном](COORDINATOR_CAPACITY_2026-10-03.md).
Здесь fixture-петля claim знает два drawId и проверяет актуальный vault.reward.
Это не измерение его event scanner или полного consumer replay.

Участники не выведены из BUY: fixture вручную публикует и замораживает проверяемые
artifacts до измерения. Общий scheduler получает только уже frozen obligations;
новые jobs и admission отключены штатными `allowNewJobs:false / obligationsOnly:true`.
Флаг «verified» в файле не добавляется; publication верифицируется обычным worker.
Нет проверки большого BUY→index→API контура в одном запуске.

RNG — заранее фиксированный LocalRandomFixture, quote — LocalUSDGFixture.
Используются прежние capacity-fixture Short rules/10 весов и Monthly V2, minimumUnit1,
Short budget1000 и Monthly budget1000 **сырых тестовых единиц**. Это не1000 реальных
USDG, не изменение launch-plan/продуктовой математики, не proof публичного drand.
Public RPC не используется; короткая доступность его истории не влияет на замер.

## Что проверяет инструмент

1. Полностью публикует оба набора, доставляет фиксированный seed. Это подготовка,
   её время записано отдельно и не выдаётся за scheduler throughput.
2. На одинаковом EVM snapshot сравнивает по одному **холодному** проходу с лимитами
   2/8/32; сбрасывает приватный cache и сохраняет отдельные journals каждого варианта.
   Эти три измерения не являются steady-state benchmark.
3. Полностью доводит оба draw до terminal с лимитом8, затем выплачивает все prizes.
4. Во время обработки останавливается после одной подтверждённой отправки.
   Отменённый повтор не меняет nonce, progress или казну. Новая программа Node
   подключается по loopback HTTP и продолжает из того же файла/контрактов без cache.
   Это реальный новый процесс, но не принудительное убийство посреди broadcast.
5. Родитель продолжает после child. Его private cache также холодный; две холодные
   точки явно выделяются, чтобы не смешивать их с обычной скоростью долгоживущего worker.
6. После выплат восстанавливает ранние main/scheduler files, сохраняет более новые
   рядом в `.completed`, очищает cache и делает два прохода без отправок. Цепочку
   при этом не откатывает. Проверяет тот же nonce и все части баланса vault.
7. Сверяет Short и Monthly resultHash с независимыми полными моделями, reward=0,
   реальные ERC20 balances победителей и сумму убыли vault. Hashes отправок уникальны,
   прирост nonce равен числу отправок; обычный idle также не отправляет ничего.

Счётчики — JS provider API calls, не HTTP requests/billing. Число записей — замены
файлов state через rename, не измеренный physical disk traffic. RSS — отдельный
sample после прохода, не полный peak process memory. Интервальные паузы watch-loop
не выполняются; их стоимость можно рассчитать отдельно по числу проходов.

314 processing +2 finish +11 claims. Все327 hashes уникальны, nonce вырос ровно
на327. Short распределил999, Monthly1000 сырых тестовых единиц. Балансы11
победителей совпали с полными моделями; vault уменьшился с2100 до101,
reserved/claimable0, остаток — freeShort1 + freeCurrent100.

Приватный cache работает и внутри общего scheduler: обычный проход читает8
транзакций текущих отправок; старые314 публикаций повторно не перечитываются.
Холодный проход лимита8 читает322 транзакции. Верхняя граница14,11s включает
последний полный processing-pass, в котором уже выполняется подготовка к finish;
это не свидетельство постепенного падения скорости.

Остановка произошла на nextChunk Short13 / Monthly12. Отменённый повтор сохранил
эти значения, nonce и казну. Новый Node-процесс за40,01s прошёл холодную проверку
и продолжил до17/16. Его wall time40,18s, RSS sample263,0MiB. После возврата
родитель также прошёл холодную проверку — его cache не делится с child.

Основной процесс совмещает worker и Hardhat EVM: sampled RSS2714–2851MiB.
Это не замер RAM боевого worker и не доказательство достаточности4GB сервера:
индекс/API/история/долгий uptime здесь одновременно не нагружались.

Обычный idle —0 отправок,0,99s. После восстановления ранних файлов при уже
выплаченной цепочке: первый проход27,33s,314 publication reads,0 отправок и
2 новых terminal anchors; второй1,06s,0 transaction reads/отправок/записей.
Более новые журналы сохранены рядом, баланс и nonce не изменились.

## Вывод для следующего пакета

Лимит8 на327 транзакций требует минимум41 проход. При неизменном pollSeconds10
это не менее400s дополнительных межпроходных пауз — **расчёт**, не реально
выполненный sleep данного стенда. Он исключает намеренный stop, idle и прочие
возможные ожидания; это не прогноз mainnet-времени. Активные520s также включают
лишние для обычного непрерывного запуска холодные проверки после демонстрации restart.

Следующий ограниченный шаг — политика пауз занятого/ожидающего сервиса и проверка
рабочего лимита отправок. Быстрое продолжение допустимо при подтверждённом прогрессе;
gas/RPC/RNG/unknown outcome не должны превращаться в быстрый бесконечный retry.
Изменение оперативного лимита не должно требовать ручной правки configHash журналов.
В этом пакете текущие pollSeconds/maxTransactions и runtime-код **не изменены**.

Дополнительный прогон100k через весь driver сейчас не нужен для выбора этого шага.
Контрактные50k/100k уже [измерены отдельно](DRAW_CAPACITY_FOLLOWUP_2026-10-03.md).
Большой внешний Pons loop, смешанный BUY→index→API поток, публичный RPC/финальность
и длительный soak этим результатом не объявляются проверенными.

## Воспроизведение

```powershell
$env:RH_TEST_ARTIFACT=(Resolve-Path .local/logs/verified-draw-compiled.json).Path
$env:RH_TEST_ARTIFACT_SHA256=(Get-FileHash -LiteralPath $env:RH_TEST_ARTIFACT -Algorithm SHA256).Hash.ToLower()
node scripts/benchmark-scheduler-load.cjs 100
node scripts/benchmark-scheduler-load.cjs 10000
```

Small smoke использует100 адресов и более раннюю остановку: такой набор заканчивается
за несколько проходов. Первый smoke остановился на ошибке **assert самого стенда**:
ожидаемый лимит считал processing/finish, но не claims в том же проходе. Проверка
исправлена; первый запуск не засчитывается как PASS. Production/runtime не менялся.

Логи: `.local/logs/scheduler-load-100.log` (неуспешный первый smoke),
`scheduler-load-100-b.log` и `scheduler-load-10000.log` (exit0).
Сырые отчёты — `.local/logs/scheduler-load-100-8h5YGf/report.json` и
`.local/logs/scheduler-load-10000-fF6YPH/report.json`. Smoke был до добавления
заключительной проверки balances победителей; большой запуск проверил итоговый код.
Полный suite не запускался: runtime не менялся, проверены непосредственно новый
стенд и полный выбранный execution path. Боевой и ручной wallet-стенд не трогали.
