# Short: расчёт обеспеченной корзины на Solidity

15.09.2026. Реализован один компонент будущего Short controller: [ShortPrizeBasket.sol](../contracts/ShortPrizeBasket.sol). Принятые правила — раздел 8 [PRODUCT_SPEC](PRODUCT_SPEC.md). Численные настройки не утверждались этим изменением.

## API и поведение

Внутренняя pure-библиотека `build(budget, weights, minimumUnit)` возвращает `(prizes, total, remainder)`. Все значения — целые raw units призового актива. Адреса, decimals и внешние контракты библиотеке не нужны; отдельный library deployment/linking не требуется.

```text
sum = сумма положительных weights
unit = floor(budget / sum)
unit < minimumUnit → BudgetNotReady
prizes[i] = unit × weights[i]
total = unit × sum
remainder = budget − total
```

Пустой шаблон, нулевой вес, нулевой минимум и сумма весов сверх uint256 отклоняются как `InvalidTemplate`. Нулевой или недостаточный бюджет при корректном шаблоне — `BudgetNotReady`, а не корзина нулевых выигрышей. Минимум применяется к базовой единице, даже если каждый вес больше единицы.

Расчёт порога через деление избегает переполнения `minimumUnit × sum`. Каждый приз и их сумма ограничены budget. Гарантируется `total + remainder = budget`, `remainder < sum`, положительность всех призов и сохранение числа мест при росте бюджета. Порядок весов сохраняется; это ещё не случайный порядок выдачи.

## Граница компонента

Библиотека не выбирает D, не фиксирует шаблон, не резервирует деньги и не проверяет участников/random. Она пока **не подключена к production controller**, которого ещё нет. Перед запросом random будущий controller должен зафиксировать бюджет, шаблон/корзину, правила и участников; после этого funding не должен пересчитывать корзину. Вызов pure-функции сам по себе такой гарантии не создаёт.

Лимит production K и способ обработки большого списка остаются частью controller-дизайна. Сейчас вычисление линейно по числу весов; произвольное ограничение K не добавляли. Ни permission model PromoVault, ни его существующие reserve/finalize не менялись. Произвольная передача winners через тестовую заглушку не является реализацией честного розыгрыша.

## Проверки

`npm run test:short:basket` запускает шесть тестов. В том числе 64 детерминированных набора шаблонов/бюджетов, границы uint256, порог готовности, округление и рост номиналов без увеличения K.

Интеграционный сценарий использует настоящий PromoVault и test-only controller: 223 raw units в Short → резервирование → ещё 77 funding → назначение двух призов 70 и 10 из рассчитанной корзины → отдельный no-win → получение старых наград. Итог: 80 выплачено, 220 осталось в Short, долгов и reserved нет. Неиспользованные места и пыль не исчезают; новое funding не меняет уже резервированный бюджет. Выбор двух мест задаёт тест, не RNG.

Полный `npm test` включает эти проверки вместе с существующими FeeRouter/PromoVault tests. Сетевые PAIR/fork проверки для pure-расчёта не нужны.

Результат 15.09: **51/51 tests passed** (45 существующих и 6 новых), включая Solidity compilation.

Фиксация snapshot и корзины с настоящим резервом теперь реализована отдельным внутренним [ShortDrawCommitment](SHORT_DRAW_COMMITMENT.md). Там weights/minimumUnit неизменяемы для уже frozen draw; будущий может получить другую версию. Есть технический предел 64 места; сама pure-библиотека не менялась. [Outcome](SHORT_OUTCOME_VERIFICATION.md) рассчитывается на Solidity/JS и проверен с test-only terminal. Полный production controller и подтверждение entries/random ещё не реализованы; MVP не готов к запуску.
