# PAIR: полученные исходники и воспроизводимый запуск

15.09.2026. Продолжение [первого аудита](PAIR_DEPENDENCY_AUDIT_2026-09-15.md). Production-контракты не изменены. Продуктовые правила находятся в PRODUCT_SPEC; этот документ описывает доказательства и план реализации переносимости.

## Что удалось проверить

Исходники доступны через **Sourcify API v2**, хотя старые repository URL отвечали 404, а Blockscout — 403. Сохранены восемь выбранных MIT-файлов в [research/pair-source-audit/sources](../research/pair-source-audit/sources). Это внешние справочные исходники, не часть нашей сборки.

[Manifest](../research/pair-source-audit/manifest.json) содержит адреса, URL первоисточников, блок, ответы RPC, compilation metadata и хеши файлов. Для семи deployments Sourcify сообщает `exact_match`; runtime из его записи побайтно совпал с `eth_getCode` на одном свежем блоке chain 4663. Хеши сохранённых исходников проверены по metadata. Независимую перекомпиляцию внешних контрактов не выполняли.

Воспроизведение: `node scripts/pair-source-audit.cjs`. Нужны установленные npm-зависимости, публичные RPC и Sourcify; кошелёк не нужен, транзакций нет. Команда обновляет snapshot и файлы; изменение implementation или выбранного registry останавливает проверку, а не автоматически принимает новый граф.

| Компонент | Результат чтения исходников | Значение для нашего продукта |
|---|---|---|
| Native fee-sharing handler V5 | Создаёт FactoryV2; mode 1 допускает community takeover | Нельзя считать будущий creator revenue безусловно закреплённым за нашим router |
| FactoryV2 / VaultV2 | Factory использует `new ...{salt:...}`; `upgradeVaultImplementation` всегда revert | Проверенная ветка vault не использует заменяемую implementation. Это не обещание неизменности всего PAIR |
| Registry | `communityTakeover` может сменить recipients без согласия прежних получателей; для этой версии вызывает atomic transition | Поток будущих комиссий может уйти от router; знание имени администратора ничего не меняет |
| VaultV2 transition | Собирает fees всех зарегистрированных позиций в старый epoch, затем открывает новый; старые claimable не переписывает | Наши старые credits и будущие поступления нужно рассматривать отдельно |
| VaultV2 collect | 70% creator / 30% protocol; protocol доля сразу отправляется treasury | Ошибка этого token transfer откатывает collect, даже если creator recipient исправен |
| VaultV2 LP | В исследованном коде нет вывода LP, approval для передачи LP, burn/decrease или произвольного внешнего вызова | Нельзя планировать повторный запуск за счёт автоматического переноса старой ликвидности |
| Legacy PairV4Locker | Отдельный контракт, хранит credits обеих сторон | Его нельзя выдавать за custody native V2 позиции; для native ветки custody находится в vault |
| Native hook | Swap callbacks не обращаются к серверу PAIR или priceSigner; beforeSwap читает on-chain stateView | Выключение сайта само по себе не равно остановке этого swap path; сеть, токены, PoolManager и stateView остаются зависимостями |
| Launchpad | Implementation upgradeable. Канонический `launchV2Token` выбирает active registry (либо fallback), затем `currentCoordinator()` | Проверен выбранный registry. Getter `launchV2Coordinator()` относится к другому маршруту и не доказывает разрыв канонического графа |

VaultV2 исходник получен из верифицированной компиляции factory, которая включает его создание. Это **не** проверка ещё не существующего vault нашего токена. Исторический public vault `0xd1ade…` не идентифицирован как этот V2. PositionManager, токен и все транзитивные зависимости этим проходом полностью не аудированы; запуск собственного токена на fork заново не проводился.

## Принятая граница переносимости

PAIR — первая площадка торговли и получения комиссий. Собственная призовая система должна допускать **новое независимое развёртывание** на другой совместимой площадке. Это не hot migration существующего контракта и не право изъять старую призовую казну.

```text
Площадка A: TOKEN / рынок → конкретный сборщик комиссий → конвертация → PromoVault A
Площадка B: новый рынок  → свой сборщик комиссий        → конвертация → PromoVault B
                                      внешнее funding → соответствующий PromoVault
```

У A и B свои адреса, средства, обязательства и участники. Повторно используем код и продуктовую логику. Старые claimable остаются в старом экземпляре; перенос TOKEN, holders, LP и резервов не возникает от смены RPC или конфига. Судьбу старого рынка и запуск нового токена придётся объявлять отдельно.

## Что уже переносимо, а что придётся адаптировать

| Часть | Сейчас | При повторном запуске |
|---|---|---|
| PromoVault | Нет вызовов PAIR; адреса token, quote, controller и target задаются в constructor и immutable | Повторно развернуть с проверенными активами и controller. Проверить decimals и raw units |
| Funding и резервы | GENERAL 3:2:1 с overflow Next → Current зашит в код | Иная пропорция требует новой версии кода и тестов, а не изменения конфига старого vault |
| FeeRouter | Конкретный PAIR vault/position API и одноразовая привязка | Новый источник требует отдельной явной реализации/адаптации; готового универсального адаптера нет |
| Конвертация | Production TOKEN → USDG ещё отсутствует | Выбрать ликвидный маршрут, ограничения цены и исполнителя для конкретной площадки |
| Entries/indexer | Production ещё отсутствует | Правила допустимых BUY и декодирование событий зависят от рынка; ключи должны разделять chain и экземпляр продукта |
| Short/monthly/controller/RNG | Есть accounting и локальная модель, полного production исполнения нет | Сохранить продуктовую механику, отдельно проверить доступность RNG и исполнителей |
| Сборка/deploy | Текущая сборка ориентирована на Cancun | Проверить EVM целевой сети, зависимости, RPC, gas и воспроизводимость deployment |

Текущий продукт сохраняет USDG как призовой номинал. Другая quote-монета технически параметризована, но её выбор для нового продукта — отдельное явно объявленное решение, не скрытая подмена USDG. Target 100 USDG также переводится в units конкретного токена, а не копируется сырым числом.

## Минимальный следующий пакет работ — предложение

1. Описать deployment manifest экземпляра: chain, активы/decimals, источник комиссий, position, controller, target, версии кода и экономические допущения. Отделить constructor-параметры от правил, требующих новой сборки.
2. Подготовить повторяемое локальное развёртывание ядра с обычным тестовым ERC20 funding. Проверять независимость от PAIR на цепочке funding → reserve → finalize → claim, включая старые обязательства.
3. Для первой реальной интеграции оставить конкретный PAIR collector. Новую реализацию сборщика писать после выбора второй площадки и её API; универсальные arbitrary calls, proxy и admin withdraw не добавлять.
4. Перед запуском выбранной площадки повторить canary: создать свою позицию, собрать реальные fees, проверить rollover/claims, конвертацию и полную выплату. Подставить измеренную доходность в экономическую модель, не переносить условные 0.5% оборота как факт.

Не требуется сначала выяснять личности всех внешних администраторов. Требуется знать, какие внешние действия могут оборвать доход, чтобы новый запуск не зависел от обещания сохранить старый поток.

## Проверки этого прохода

Источник/metadata hashes и runtime equality семи deployments проверены скриптом. Существующие 27 PromoVault unit tests прошли. Это проверяет текущую локальную реализацию, но не доказывает готовность другой сети или полного production pipeline. Наши Solidity-контракты в этом проходе не менялись.
