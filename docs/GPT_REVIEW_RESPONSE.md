## Подтверждённые дефекты пользовательского слоя

1. **Средний, история розыгрышей теряет/дублирует строки.** `scripts/public-status.cjs:11–15,30` строит историю в обратном порядке и режет её по числовому offset; `web/overview.js:7–10,32,37` сохраняет offset между запросами. Обычный сценарий: пользователь посмотрел первую десятку, появился новый draw, он нажал «Older draws». Элемент на границе повторяется, один старый результат смещается на следующую страницу; после reorg или уменьшения истории offset вообще может стать вне диапазона. Минимум: курсор с идентичностью snapshot (head hash/ledger hash и позиция) и отказ/сброс на первую страницу при смене поколения; либо клиент проверяет hash и заново начинает историю. Адресный тест: между запросами страниц добавить новый draw и затем откатить head; ни дубликатов, ни молчаливой потери, явное обновление списка.
2. **Средний, поздние выигрыши не видны в кошельке.** `scripts/user-status-api.cjs:30–31` отдаёт rewards в порядке накопления и первые 25; `web/app.js:104,117–123` всегда запрашивает первую страницу и не использует `nextOffset`. Если у адреса больше 25 наград, новые назначенные и неоплаченные призы не появятся в таблице: будет только «Showing 25 of N», без способа открыть остальные. Минимум: новые награды первыми либо доступная пагинация с привязкой к snapshot; лучше оба свойства. Адресный сценарий: 26 наград, последняя assigned — её сумма/status/assignment должны быть доступны на сайте, включая после обновления снимка.

Предыдущее замечание про пропадающие frozen tickets исправлено: `web/app.js:107–111` выводит `frozenByDraw` отдельно; silent restore теперь требует именно сохранённый разрешённый адрес (`web/app.js:72–73`). Публичный UI отделяет stale/unavailable от нулей, reward amount берёт из проверенного asset наблюдения, не из произвольного quoteDecimals. В этих границах иных подтверждённых дефектов начисления/выплат по чтению не нашёл.

## Непроверенные риски и граница доказательства

- **Главный пробел, а не найденный баг:** `scripts/release-rehearsal.cjs` переносит участников из saved BUY evidence в новую локальную цепочку, готовит datasets helper и применяет виртуальное время/исторический drand. Sequential fork в `LAUNCH_PREPARATION` покрывает только collector → PAIR. Нигде пока не доказан непрерывный admitted PAIR → фактическая BUY → индексатор → автоматическая фиксация обоих snapshots → public wrappers/drand → начисление/выплата → тот же API. Старые fixture odds и корзина не равны текущим 0.8e/(e+1), 7:4:2:1×7 и Monthly V2. Зелёный `test:review` тоже не закрывает этот пробел.
- **PAIR и адреса:** `scripts/prepare-pair-launch.cjs:27–44` рассчитывает CREATE collector из nonce и TOKEN из identity/salt, а `:30–31,43,53` ещё содержит неопубликованную metadata URI, draft protection и короткий deadline. Самостоятельные `eth_call` и estimates не резервируют nonce; перед подписью нужно повторить свежий sequential fork и сверить **точные байты** calldata, адреса/chain/value/fee/gas с актуальным pending nonce и окончательной metadata. Текущий файл честно ставит `authorizationToSend:false`; не переименовывать в signable путём заполнения null без отдельного review. PAIR UI с creator-account в modeData отправил бы комиссии мимо collector; Developer Buy/произвольный UI router не доказывают допустимость BUY.
- **Наблюдение не admission:** `scripts/public-status.cjs:25–27` вычисляет funding/time по сохранённому резерву и текущему wall clock, выставляя `awaitingChecks`; это не готовность executor/RNG/finality, что API явно отмечает. Индексатор публикует свою версию данных; подпись/контрактное обязательство не доказывают полноту BUY. При восстановлении должны совпасть block hash, policy anchor, receipts, dataset и договорённый cutoff, а не только цифры в UI.
- Продакшн профиль пока неполон: archive RPC и fallback не квалифицированы, operations/executor и custody, notice/gas/native/timing, deployment/source/proxy pins и опубликованная metadata не утверждены. На сервере API `awaitingDeployment`/503 — ожидаемо, **не** live индексатор. Полная стоимость развёртывания и запас ETH не известны. Никаких mainnet sends до закрытия этих границ.

## Один ближайший пакет и порядок после него

**Следующий ограниченный пакет:** построить воспроизводимый **same-chain collector → PAIR → admitted direct BUY → persistent indexer → entries** на одном локальном fork/state и закрепить машинный отчёт: chain/head hashes, tx receipts, source/collector/pool/route, net debit, carry, policy anchor, restart без дублирования. Никакой ручной передачи участников/helper mint. Отдельные 101 и 60+40, отрицательные sell/unsupported route. Если для fork нужны impersonation, тестовые USDG или time travel — перечислить их в отчёте; контрактные параметры и public config не подменять. Эта часть уже найдёт наиболее опасную дырку на стыке PAIR и билетов, не заставляя сразу симулировать месяц.

После неё: (1) эти же ledger/snapshot через оба public draw и независимый drand proof, win/no-win, vault/claim; (2) restart/failure injection и сквозное чтение API/browser, исправить пагинацию; (3) полный baseline на commit; (4) отдельный deployment review финальных immutable/ролей, metadata, source/bytecode, RPC, газа, custody/backup/alerts и юридических условий. Каждое доказательство фиксировать вместе с допущениями. Public activation лишь после совокупного прохождения и отдельного утверждения конкретных транзакций; текущие guards остаются закрытыми.
