## Наблюдения по приоритету

1. **Высокий для нагрузки RPC при длительном индексировании; газ = 0.** `scripts/replay-direct-buy.cjs:46–67` читает целые блоки и receipts всех транзакций. Для batch-профиля на **каждом** блоке проверяет parent code executor, on-chain bindings и код всех закреплённых адресов, даже при отсутствии целевого события. Для каждой посторонней self-транзакции дополнительно читает `eth_getCode(payer, parent)` *до* получения receipt (`:64–65`). Это несколько исторических запросов на пустые блоки и ещё запросы по чужим аккаунтам; точную цену в рабочем RPC пока не измеряли. Первое безопасное сокращение: запрашивать parent code payer только после receipt с потенциальным целевым BUY; чужая self-транзакция без такого события не может дать билет. Проверки закреплённых контрактов/исторического состояния не пропускать вслепую: если переносить их на блоки с релевантными событиями, отдельно доказать, что нельзя пропустить drift и policy boundary. Контроль: число вызовов по методам и время на 100–1000 типичных блоков, пустых и с BUY; reorg и кандидат с недоступным parent code должны по-прежнему давать консервативный отказ. Прежний ответ уже отмечал случай чужих self-calls.

2. **Средний, дешёвая перестановка; газ = 0.** В `scripts/local-promo-scheduler.cjs:177–185` новая попытка сначала делает `resolveBuyPolicy` (исторические logs/code/receipts/calls), лишь потом читает `lastShortTerminalAt`/`lastMonthAt` и интервал и возвращает `schedule` до срока. На каждом обычном тике двух направлений это повторяется, хотя создание job пока невозможно. Проверить расписание до тяжёлого admission; после достижения срока выполнить тот же полный admission и остальные проверки. Исторические/сохранённые jobs (`:72–175`) при этом идут первым делом и не должны ждать интервала. Измерить RPC/tick на неподходящем сроке и на границе срока, проверить смену policy и две эпохи.

3. **Средний для долгоживущего процесса; газ = 0.** `scripts/persistent-buy-indexer.cjs:75–94` сохраняет весь массив блоков, receipt/cache и ledger JSON с checksum, `fsync` и `rename` на каждом poll, даже когда `end===base`; при новом блоке replay делает проход по всей истории. `readSnapshot:24–29` снова проверяет prefix и делает replay перед scheduler, который повторяет lifecycle replay и перед begin сверяет независимую реконструкцию (`local-promo-scheduler.cjs:148–162,193–245`). На малой истории это нормально, но дисковые байты и CPU растут с возрастом проекта, а snapshot metrics уже содержит `replayMs`, `saveMs`, `stateBytes`. Сначала снять график этих трёх полей и RPC/tick на длинной истории; затем отделить компактный журнал/checkpoint от публикуемого snapshot либо сократить *доказанные* повторные вычисления с той же branch/revision/manifest identity. Не превращать persisted minted totals в источник открытых билетов и не убирать независимую проверку перед begin.

4. **Средний операционный резерв, не переплата газа.** В `scripts/pons-automation.cjs:44–60` перед любой отправкой guard требует `nativeFloor + (20 + payouts + 2×expectedCount + ...) × gasLimit × maxGasPrice`; базовые 20 вызовов при лимите 3 млн gas и потолке 10 gwei означают резерв **0,6 ETH плюс floor** даже без участников (при указанном профиле). Средства остаются на кошельке; этот расчёт может преждевременно дать `nativeFunding` и задержать приз/розыгрыш. Не снижать запас на глаз: сопоставить сохранённые реальные `gasUsed`, `estimateGas`, верхние границы per-action и число оставшихся обязательных транзакций; отдельно обеспечить runway для уже frozen выплат. Сначала показать частоту ложных ожиданий, потом менять формулу.

5. **Низкий сейчас, масштабируется с кампаниями; газ = 0.** `scripts/pons-collector-manual.cjs:11–41` при каждом inspect перечитывает все policies с `1..campaignId`, credits адресов и симулирует все готовые действия. `pons-funding-pass.cjs:3–12` заново inspect после каждой предпринятой отправки — это правильно для изменённого on-chain state, а на idle уже переиспользуется один plan. Но план pass содержит только `pay-prizes/ops/team` **текущей** кампании; старые адреса представлены как `pay:<address>` и не входят в ACTIONS. При rollover сканирование старых кампаний дорожает, а их credits автоматически не выплачиваются. Сейчас coordinator закреплён за campaign 1, так что не выдавать это за текущую потерю. Перед поддержкой rollover определить явный проход по старым due credits и ограничить нужные RPC, сохранив возможность pay при отказе sweep/escrow.

## Не резать без нового доказательства

- `LocalPonsCollector.pull()` уже вызывает `_sync()`; следующий `sync` в funding pass после успешного pull обычно определяется как `empty` без транзакции (`contracts/LocalPonsCollector.sol:149–166`, `pons-funding-pass.cjs:3–12`). `pay` вызывается только при credit>0; inspect не отправляет sweep при `quoteDue=0`. Повторное чтение/симуляция стоят RPC, а не on-chain gas.
- `pons-automation.cjs:94,100,112` вызывает claims трижды за проход. Последующие проверки обычно не сканируют старую историю после сдвига cursor, но могут увидеть новые события после settlement и scheduler. Убирать вызов только вместе с проверкой порядка обязательств, а не по одному счётчику RPC.
- Checkpoint на пустом интервале отсекается предварительным replay (`local-promo-scheduler.cjs:193–205`); `closeEmpty` завершает draining epoch. Chunked settlement, финальность и независимая сверка replay расходуют операции ради ограниченного газа на вызов и корректных выплат.

**Практический следующий пакет:** сначала лёгкий порядок schedule→admission и фильтр parent-code reads с адресными регрессиями и счётчиком RPC; параллельно собрать метрики `replayMs/saveMs/stateBytes`, gasUsed операторских receipts и долю `nativeFunding` при достаточном фактическом балансе. Только по этим данным выбирать формат долговременного индекса и запас ETH. Это не блокирует отдельное G10 исследование реально исполненного 0x маршрута, но до production нужен повторный замер на целевой инфраструктуре.
