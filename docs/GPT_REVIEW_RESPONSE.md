## Выбор архитектуры

Для нашего deployment я бы **начинал с Swap разрешённого pool id**, а TOKEN
Transfers искал в полной квитанции как обязательное доказательство доставки.
В V4 PoolManager общий; нужен конкретный pool id, направление и включённая версия
политики. Это точнее TOKEN-first: transfer виден также при gift/LP/claim/bridge,
а адрес `from`/`to` сам по себе не устанавливает плательщика и владельца BUY.
Текущий replay уже читает все receipts и ищет Swap; менять семантику обнаружения
ради широкого Transfer-фильтра не требуется. Фильтр Transfer допустим только как
ускорение после отдельного доказательства, что он не пропускает поддержанные BUY.
Если будущий TOKEN торгуется в других пулах, каждый pool/key и способ оценки
должны быть явно включены в версионную политику, а не выводиться из адреса TOKEN.

Минимальный путь: `pool Swap → candidate (chain/block/tx/logIndex/poolId) →
проверенный route adapter → payment + TOKEN delivery → один зарегистрированный
participant → однократный eligible USDG`. Adapter возвращает используемые
Swap/Transfer log ids и единое обязательство по средствам; разные adapters
не могут засчитать пересекающиеся логи или один USDG дважды. Пропуск одного
проверяемого звена даёт `UNSUPPORTED`/`AMBIGUOUS`, не эвристику «последний адрес
в цепочке — человек». Независимый replay остаётся от anchor по полным receipts;
индекс кандидатов не становится источником истины.

Общее settlement rule полезно для проверки направления, сумм, непересечения
логов и сохранения USDG; **одних receipts недостаточно** для связи оплаты,
ордера и участника во всех маршрутах. Нужен route-specific calldata/путь и
проверенная семантика исполнения конкретного runtime. Контрпримеры: два Swap
с одним net settlement; USDG одного кошелька и TOKEN другому; split/refund или
fee, где общий input больше оплаченного target BUY; gift после Swap; внутренний
кредит router/solver вместо денег участника. Не приписывать всё по одному
`tx.from`, `Swap.sender` или итоговому balance delta.

Правило `payer == finalRecipient == registered wallet` оставить для MVP.
`tx.from` может быть relayer: для отдельного smart-wallet adapter допустимо
доказать, что **сам зарегистрированный контрактный wallet** разрешил операцию,
оплатил свой BUY и получил TOKEN, даже если outer sender иной. Это сохраняет
экономический смысл равенства. Реальный `payer != recipient` (подарок,
агрегаторский inventory, solver) не засчитывать без нового продуктового решения
о бенефициаре и защиты от фарминга; регистрации одного recipient недостаточно.

## Какие маршруты разбирать

1. Уже поддержанные direct USDG→TOKEN формы — baseline. Следующий кандидат:
   одна ограниченная вариация **того же router**, например наблюдённый `0x0a10`,
   только после receipt нашего разрешённого пула и доказательства значения
   дополнительной команды, payer, settlement и получателя. Нынешний sample
   чужого пула не доказывает её пригодность.
2. Один точный multihop `asset→USDG→TOKEN` в выбранном router. При
   единственном однозначном USDG→TOKEN leg зачёт по **actual USDG delta этого
   разрешённого пула**, с доказанной оплатой/получателем и без повторного
   использования USDG в batch. Исходный актив сам по себе не требует оракула.
3. PAIR AUTO либо wallet/solver — позже как отдельное семейство по реальному
   receipt, source/runtime и проверенной модели attribution. Бренд и allowlist
   адресов этой модели не заменяют. `USDG→stock→TOKEN` не имеет USDG в
   последнем V4 pool; входной USDG нельзя просто целиком отдать каждому TOKEN
   leg при split/refund/fees. Маршрут без доказуемого относящегося USDG пока
   не создаёт попыток; без-USDG покупка требует отдельного правила оценки и
   решения владельца, не скрытого oracle.

Критерий допуска семейства: сохранённые block/tx/receipt и runtime/ABI
конкретного deployment; однозначные payer/recipient/USDG; позитивный реальный
путь и негативные gift, batch, refunds, mixed funds, pre-registration, reorg;
детерминированный replay с непересекающимися evidence ids; будущая публичная
активация. Частоту использования после запуска измерять отдельно; короткая
общая выборка не позволяет ранжировать семейства по market share.

## Пользовательский статус и следующий пакет

На сайте показывать «начислено» только после принятого replay/finality;
«проверяется» — только пока конкретная tx ждёт finality/разбора; затем
окончательный статус «не зарегистрирован», «маршрут не поддержан» или
«свидетельства неоднозначны» с понятной причиной. Transfer-only не называть
покупкой. Будущая активация adapter не обещает задним числом начислить билеты.
Точную допустимость рекламы/промо в РФ решать отдельно с юристом по фактической
механике и текстам; название сайта юридической оценки не заменяет.

**Один следующий implementation пакет:** закрыть policy admission до добавления
нового route. Вместо произвольного JSON announce — типизированные конечные
переходы `schemaVersion/adapterId/fromBlock` из проверенного набора; source
проверяет id, последовательность и notice, verifier детерминированно строит
manifest от genesis. Для ещё не известного adapter — новый явно принятый
source/schema с публичной связью старого hash и историей, без тихой смены trust
или переписывания frozen. RPC CLI обязан явно различать admitted instance и
unadmitted/offline genesis: отсутствие `buyPolicy` не должно выдавать v2 за
проверенное обновление. Vectors: валидный переход, unknown id, дублирование,
ранний block, ошибочный payload, отсутствие trust, пропуск последнего notice,
old pending/settled snapshot, reorg. Независимый replay persisted job перед
первым begin остаётся отдельным обязательным релизным gate; самосогласованный
checksum не доказывает участников. После этого брать **один** receipt нашего
пула и делать следующий route adapter, не универсальный graph engine.
