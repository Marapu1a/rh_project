## Findings по серьёзности

### P1 — подтверждённая гонка журнала Claim между вкладками

`web/claim.js:43–55,57–67`: `send` удерживает Web Lock, но `check` читает и **записывает** тот же ключ без lock и без проверки, что прочитанный hash ещё текущий. Конкретный порядок: A имеет сохранённый pending hash, его receipt reverted; вкладка 1 начинает `check(A)` и задерживается на RPC. Вкладка 2 получает reverted, под lock заново проверяет невыплаченный prize и отправляет B; журнал уже `pending(hash=B)`. Запоздалый `check(A)` пишет `{...saved, state:'reverted'}`, стирая B. После этого UI/другая вкладка может отправить C, пока B ещё pending. Контрактный `reward` не должен дать две выплаты, но две конкурирующие транзакции, потраченный газ и ложное состояние кабинета возможны. При automatic payout гонка также не оправдывает потерю hash B.

Минимум: сериализовать **все записи** журнала по тому же ключу, либо перед записью результата `check` атомарно сравнивать текущие `hash/state` с прочитанными под общим lock; при расхождении не перезаписывать, показать новый статус. Даже под lock повторная сверка после RPC сохраняет понятный инвариант. Тест: общий storage, настоящий/управляемый lock двух экземпляров, задержанный ответ receipt A, между чтением и записью проверка reverted и отправка B; после отпускания A сохраняется B, третьего `eth_sendTransaction` нет. Отдельно то же при `confirmed` и при смене аккаунта. Это блокер **тестового кандидата** до адресной проверки; исправление не требует менять контракт/призы.

### P2 — подтверждённый UX дефект: фоновый refresh отменяет открытый Claim review

`web/app.js:102–109,141–164,183`: каждый `refresh()` увеличивает `version` **до** получения данных; таймер делает это каждые 30 секунд при открытой вкладке. `claimEngine.current` и кнопка подтверждения привязаны к этой версии. Пользователь может увидеть проверенную сумму и газ, читать диалог чуть более 30 секунд и нажать Confirm: подтверждение отклонится сообщением «wallet or data changed», хотя account, chain, prize и deployment не изменились. При refresh между этапами `prepare` это также закрывает операцию. Денежной ошибки здесь не видно, но для ручного запасного Claim это воспроизводимый отказ UX.

Минимум: инвалидировать review при **реальной** смене account/chain/provider, deployment или значимого prize state, а фоновые одинаковые снимки не считать изменением. Перед send всё равно выполнять уже существующий свежий on-chain `prepare/context`. Тест: открыть review, дождаться одного/двух автообновлений с тем же API, подтвердить ровно один send; изменение сети/аккаунта и новый amount обязаны закрыть старый review.

### P2 — устойчивость: восстановление неизвестного исхода Claim отсутствует

`web/claim.js:48–66`, `web/app.js:155–165`. Это **известное ограничение**, не новая ошибка допуска: `submitting` без ответа provider и `unknown` без hash навсегда подавляют повтор в данном origin; `check` при отсутствии hash просто возвращает состояние. Оно безопасно против слепого повтора, но если провайдер потерял ответ/пользователь сменил устройство, пользователь не может в кабинете доказать ни включение, ни отсутствие транзакции. При принятом автоматическом payout это не ломает нормальную выплату, но ручной fallback застревает. Замена/ускорение транзакции с другим hash также остаётся в pending старого hash. Не предлагать кнопку «сбросить и повторить».

Для тестового этапа достаточно честно зафиксировать операторский/пользовательский recovery сценарий: lookup по строго проверенному hash, возможно введённому пользователем, или поиск операции по nonce/account с последующей проверкой canonical receipt, точных calldata/value/vault и `reward`; неоднозначность оставлять заблокированной. Тест: поздний hash, replacement и unknown без hash; ни один сценарий не разрешает вторую отправку, пока исход первой неизвестен. Полный автоматический recovery разных устройств относится к будущему product scope.

Даже `unchanged` переписывает снимок. ### Гипотезы и ограничения доказательств, без статуса дефекта

- `persistent-buy-indexer.cjs:81–87`: на idle `unchanged` проверяет наличие checkpoint schema, но не сверяет его `head/ledgerHash` с ledger и prefix; на append `replayEngine` делает более строгую проверку. Обычный checksum не является независимым доказательством содержимого. После согласованного внешнего изменения файла или ошибки записи производного checkpoint это могло бы отложить обнаружение до append/audit; не вижу из кода способа получить такое состояние из текущей атомарной записи при нормальном запуске. Адресный тест на неконсистентный, но правильно пересчитанный локальный snapshot и сравнение idle/append/audit уточнит риск. Не представлять пересчитанный checksum как модель недоверенного злоумышленника: это локальная целостность, не аутентификация.
- `web/claim.js:60–66`: canonical hash блока подтверждается на момент `check`, статус `confirmed` локален и не равен публичной финальности; `Paid` в UI идёт из независимо replayed API evidence (`user-status-api.cjs:7–19`). В этих границах ложного `Paid` или второго on-chain приза из статического чтения не нашёл. Для боевого окружения нужен отдельный finality policy.
- `pons-zeroex-buy.cjs:35–95`, `pons-entrypoint-buy.cjs:26–66`: допуск требует pinned runtime, одного pool swap и строгой последовательности USDG/TOKEN transfers, account вместо bundler и проверки parent delegation/authorization. Я не нашёл пути сделать билет из произвольного Transfer, внешнего pool, split/refund, служебного swap или failed op в этой узкой форме. `original.length===1`, весь receipt и transaction-wide relevant logs закрывают смешанный маршрут; старые genesis не получают v3/v4 автоматически (`pons-profiles.cjs`). Это вывод по коду, не доказательство отсутствия всех обходов сторонних контрактов или свойств реального Pons оператора. Новые маршруты проверены на другом токене и локальном fork; policy/lifecycle/непрерывность для index/API смоделированы отдельно. В сквозном wallet cycle использованы direct curve/v4, **не** все wrapper пути. Ключевые сырые logs и установленное расширение из опубликованного evidence воспроизвести здесь нельзя.
- `local-scheduler-state.cjs:28–35` делает fsync файла и rename, но не fsync директории. Это стандартная граница crash durability на некоторых FS, не установленная потеря snapshot. Включить power-loss/restore в A4; не смешивать с уже проверенным обычным process restart.

## Что именно закрывать до следующего этапа

**Тестовый этап A:** исправить гонку journal, проверить auto-refresh/review и явный recovery для unknown/replacement; провести admitted замер и restore с бюджетом; затем согласованный A5 baseline на одном SHA с отдельным web/Claim набором и выбранными fault/cycle сценариями. Не требуется заново доказывать каждый старый PASS на каждом рабочем коммите, но суммой частичных запусков разных деревьев нельзя заменить кандидат.

**Только боевой этап B:** реальные manifest/адреса/custody/публичные permissions, качественный RPC и историческое состояние, finality/timing на целевой сети, эксплуатационный backup/alert/внешний канал, независимая доступность Pons conversion, внедрение Claim entrypoint за пределами loopback/31337. Donor funding, управляемые finalized/часы и impersonated operator в fork этого не доказывают. Нехватка газа остаётся ожиданием с сигналом, без обязательного большого ETH резерва; frozen/claimable не становятся бюджетом операций.

**Последующее расширение:** native/partial/refund/split/multi-op/paymaster, новые account implementations и рынки, QR/WalletConnect, полная история покупок с пагинацией. Не начислять билеты задним числом или по признаку «старый/рабочий кошелёк».

## Следующий ограниченный пакет устойчивости (4 проверки)

1. **Admitted история и бюджеты.** Репрезентативные плотности curve/v4/0x/EntryPoint, реальные lifecycle/rewards/public projection и API worker: 10k/50k/100k блоков или достижимый масштаб с зафиксированным tx/BUY/draw mix. Измерить p50/p95 poll idle/append, full audit, snapshot bytes, peak RSS/heap, количество RPC, API cold reload и 32 параллельных wallet reads, coordinator cutoff. Заранее записать budget: p95 poll + API reload укладываются в половину `maxAgeSeconds`, без роста backlog, OOM и повышения freshness timeout. Если нет, оптимизировать измеренный полный проход/формат; решение о сегментации принимать по профилю.
2. **Сравнение checkpoint с полным replay.** На одной зафиксированной evidence цепочке: carry 60+40, несколько wallets, lifecycle freeze/consume, reward assigned/paid, append, idle, restart, activation policy и reorg на допустимой глубине. После каждого шага сравнить canonical ledger hash, open/frozen/consumed, payout/reserve и wallet/API результаты checkpoint против независимого full replay; никакого пересчёта старого frozen.
3. **Crash/backup/restore.** Снимать backup опубликованного snapshot + точного config и отдельно денежные journals; убивать writer до temp fsync, после fsync и после rename, восстановить новый процесс; проверить последний целый snapshot, lock/manual stale-lock процедуру, повторное догоняние canonical branch, hash/обязательства и отсутствие повторной отправки. Никакой silent reset journals. Сохранить restore time, размер backup и результат для каждого места сбоя.
4. **Конкуренция и сбои интерфейса.** Две вкладки с delayed reverted receipt A и pending B (гонка выше); 30–60 секунд review через auto-refresh; account/network change в wallet prompt, поздний hash, replacement/unknown; HTTP API outage/restart одновременно с payout. Критерий: 0 потерянных hash, не больше одной активной отправки на prize, Paid только после проверенной выплаты, отсутствие билетов/Claim при unavailable/stale; записать ручные действия, если автоматического восстановления нет.

Это ограниченный пакет тестового контура и критерии, а не предложение немедленно переписать хранение или расширить правило билетов. Подтверждённой ошибки денежной математики в узких новых BUY proof по статическому чтению не нашёл; **P1 гонка Claim требует исправления до объявления тестового кандидата готовым**. Production readiness и аудит безопасности этим review не утверждаются.
