# Постоянный ответ GPT — read-only service

29.09.2026. Статический review `93bd488`: прочитал supervisor/child/API, блокировки state, systemd unit, runbook и адресные сценарии. Tests/build/fork по договорённости не запускал.

В обычных рассмотренных отказах критического дефекта не вижу. Service берёт отдельный owner lock перед HTTP, запускает не более одного indexOnce-child одновременно и ждёт его exit перед новым проходом. Pass lock снимается supervisor только после выхода **своего** child и совпадения записанного PID; чужой или нечитаемый lock переводит сервис в `needsAttention`, не запускает конкурирующий проход. Неизвестный/повреждённый state не сбрасывается. RPC failure и timeout дают повторную попытку без изменения последнего хорошего index snapshot; закрытие останавливает новые проходы, worker API и child, затем освобождает свой service lock. Проверки настоящих дочерних процессов и mock RPC покрывают эти обычные ветки; их не повторял.

`/healthz` отдаёт 200 только при свежем `admitted` и `caughtUp` **последнем успешном проходе**; `unadmitted`, waiting, stale и внимание получают 503. Он не утверждает, что RPC доступен прямо сейчас или что wallet worker сможет прочитать конкретный кошелёк, и это честно сказано в ответе/документации. Wallet endpoint продолжает собственную проверку файла, checksum и возраста. При ошибке нового прохода health становится waiting, даже если старый snapshot ещё виден как stale в wallet API — правильное разделение.

Остаются практические границы развёртывания: после SIGKILL/power loss owner lock требует ручной проверки writers, а не автоматического удаления; systemd unit пока шаблон и не испытывался на сервере. Нужны реальные путь/пользователь/права, контроль логов и alert на длительные `waiting`/`needsAttention`. Эти вещи уместно проверять при установке, без дальнейшей гонки за абсолютной безотказностью в локальном коде.

Следующий продуктовый шаг поддерживаю: страница проекта и общий список draw с no-winner/переносом, привязанные к уже имеющимся provenance статусов покупок, билетов и наград. Затем admitted Infinity deployment/RPC и сквозной предрелизный прогон. Текущий сервис — рабочий read-only каркас, не свидетельство public launch; public sends по-прежнему закрыты.
