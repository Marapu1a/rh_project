# Постоянный ответ GPT

Обновлено: 22.09.2026.

Это независимое review-мнение, не задание на автоматическое исполнение. При следующем
обращении файл следует полностью перезаписать.

## Корректировка прошлого review

Пользователь справедливо указал, что проверки GPT регулярно краснеют не на коде, а на
разных самодельных вариантах окружения:

- запуск в синхронизируемом checkout встречает восстановленные `.local/*.lock`;
- запуск через `git archive` убирает `.git`, хотя manifest exporter сознательно читает
  git provenance;
- после этого приходится вручную объяснять, какой красный результат считать настоящим.

Такой процесс сам стал источником шума. Предыдущий результат 329/330 корректно показал
поведение exporter без `.git`, но его не следует считать регрессией основного runtime:
GPT сам выбрал среду, не соответствующую текущему контракту exporter. Portability release
bundle без `.git` можно решать отдельно, если это станет требованием продукта.

Finding с case-sensitive role addresses остаётся самостоятельным code finding: два
семантически одинаковых Ethereum address в lowercase/checksum form сейчас дают разные
budget `configHash`. Но не надо смешивать его с исправлением review-среды.

## Один следующий bounded step

Предлагаю сейчас сделать только **единый hermetic review runner** и больше не обсуждать
каждый раз локальные lock/git особенности.

Одна каноническая команда, например `npm run test:review`, должна:

1. создать уникальный detached `git worktree` текущего HEAD в системном temp;
2. гарантировать наличие рабочей git metadata (`git rev-parse HEAD` проходит);
3. запускать тесты внутри этого worktree, где `.local` физически не находится в
   синхронизируемом основном checkout;
4. явно подготовить зависимости одним документированным способом: воспроизводимый
   `npm ci --ignore-scripts` либо контролируемый reuse текущего `node_modules`, но не
   неявно рассчитывать на случайное окружение;
5. создавать runtime/test каталоги до запуска suites;
6. печатать HEAD, Node/npm/Hardhat/ethers/solc и точную команду;
7. сохранять exit code тестов и всегда безопасно удалять только созданный runner-ом
   worktree; при cleanup failure не маскировать исходный test failure;
8. не копировать untracked файлы пользователя и не трогать основной `.local`;
9. иметь короткий self-test, доказывающий одновременно отсутствие stale lock и доступность
   git provenance.

Первым каноническим профилем достаточно сделать полный `npm test`. Дополнительные fork/live
проверки в него не включать: для них нужны отдельные явные profiles и внешние prerequisites.

После появления runner-а договор простой:

- зелёный `test:review` — принимаем как локальный baseline;
- красный `test:review` — разбираем как test/code failure;
- ad-hoc запуск в основном checkout не используется для итогового вердикта;
- новый способ «чистого запуска» не изобретается в каждом review.

## Что делать после runner-а

На следующем круге GPT сначала прогонит только новую каноническую команду. Если она зелёная,
вернёмся к отдельному role-casing finding и затем к `MVP release profile v1` из прошлого
релизного аудита. В этот пакет не надо добавлять manifest redesign, venue, RNG, swap,
recovery или продуктовые параметры.

Пользовательский `docs/INDEPENDENT_AUDIT_2026-09-19.md` не изменялся.

Итог: сейчас чинится не бизнес-логика, а процедура доказательства. Один стабильный runner
дешевле и честнее бесконечной перепроверки того, почему очередной временный каталог оказался
«не совсем чистым».
