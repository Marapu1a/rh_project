## Вердикт по сделанному

Маршрут теперь действительно больше похож на проверяемый локальный MVP, чем на подмену исторического oracle текущим spot. `LocalMarketPrizeConverter.convert` возвращает *фактическую* USDG delta, и `v4-market-quote.cjs` делает `staticCall` этого же метода от адреса executor на закреплённом блоке. Выполняется та же цепочка converter → adapter → router; real send применяет положительный `minOut`, короткий deadline, ожидаемую версию и balance deltas. Quote с `minOut=1` существует только в `eth_call`; она не меняет баланс. Код adapter задаёт один PoolKey, exact-input и конкретного получателя, а не произвольный calldata. Проверки exact TOKEN debit, allowance cleanup и нулевого нового остатка на adapter выглядят согласованно. В сохранённом fork один Swap нужного poolId, Converted, actualOut и сумма трёх GENERAL bucket совпали; повторил узкий offline regression тест: **1/1, exit 0, ~19 с вместе с compile**. Это подтверждает сохранённый trace, не повторяет fork.

`0x10 / 0x06,0x0b,0x0e` и структура input подтвердились для **этого** deployment реальным fork swap. Текущий [Actions.sol Uniswap](https://github.com/Uniswap/v4-periphery/blob/main/src/libraries/Actions.sol) обозначает 0x06 как exact-input single, 0x0b как SETTLE, 0x0e как TAKE; upstream не является доказательством ABI любого будущего router release. `SETTLE` с payer=true и `TAKE` в адрес вызывающего converter были проверены через реальное исполнение и дельты, а не только прочитаны из комментария. `amount`/`minimum` ограничены `uint128` adapter, внутри converter проверяются minOut и полученный USDG. Отсутствие getter Permit2 признано честно: его адрес — deployment binding, а не runtime доказательство. Для будущего token/pool эти факты надо проверить снова.

Hash converter/adapter и getter/version/assets сверяются при pinned block; converter сам не принимает смену adapter version во время исполнения, adapter проверяет hashes своих зависимостей. Worker сверяет hash блока, возраст quote и объём, а общий send/receipt boundary сохраняет неизвестный hash и не разрешает слепой повтор. `marketQuote` хранится внутри job и coordinator identity; CLI не подставляет невидимый callback. Непроверенная RPC, выбранный publisher/executor, mutable dependencies за runtime hash, изменение рынка до inclusion и потенциальное изменение газа остаются доверенными/рыночными границами. `minOut` остановит худшее исполнение, но не доказывает уровень исходной цены.

## Два конкретных зазора в политике порций

1. **Gas cap проверяется только при выборе quote.** `v4-market-quote.cjs:42–61` считает `gasUnits * gasPrice * margin` на момент симуляции. Затем `local-prize-flow.cjs:192–202` проверяет возраст/минимум, а `sendLocalTransaction` повторно делает estimate и выставляет `gasLimit` и `maxFeePerGas` из уже текущего `getFeeData` (`local-prize-flow.cjs:123–130`). Есть общий `job.maxGasPrice`/ops budget, но повторной проверки именно `maxGasCostWei` перед broadcast нет. Если цена газа или оценка units выросли в пределах общего потолка, sale может уйти дороже заявленного market cap. Это **не обход on-chain TOKEN bucket/minOut**, а рассогласование заявленного off-chain лимита затрат. На публичной сети actual fee ещё зависит от её модели; даже повторная проверка будет ограничением tx fee по консервативному gasLimit/maxFee, не обещанием точной оплаты.
2. **Дорогой кандидат преждевременно завершает поиск.** При `gasCost > maxGasCostWei` код в строке 60 возвращает `null`. Небольшая порция может пересечь меньше ticks и уложиться в cap, хотя большая уже удовлетворяла impact/minUSDG. Это обычный путь, который существующий тест `maxGasCostWei=1` не различает: там никакой размер не должен пройти. Аналогично ошибка `eth_estimateGas` завершает подбор вместо ограниченного перехода к следующему меньшему кандидату. Не надо бесконечных повторов: сохранить `maxCandidates`, считать отказ газа поводом попробовать половину; если gas почти постоянен, быстро остановиться на нижней границе. Не обещать, что всегда найдётся выгодный размер.

При `request.amountIn < sampleInput` baseline становится самим кандидатом: сравнение удельного выхода тогда тождественно и impact-фильтр ничего не измеряет. Это допустимо только как явно объявленная нижняя зона, где `sampleInput` уже считается безопасно малой порцией **для конкретной ликвидности**. При новом/сильно похудевшем пуле такого доказательства нет; `minSampleOutput` отсекает пыль, но не высокий собственный impact. Исходная sample тоже двигает цену. Не называйте `maxImpactBps` абсолютной защитой или USDG-прибылью с учётом газа. RPC budget ограничен `1 + maxCandidates` симуляциями на converter/quote (возможна повторная sample из cache без нового call), плюс bindings/estimate; `maxCandidates<=8` и один swap/converter/pass исключают бесконечный поиск. Дорогие ответы и частый poll всё же требуют эксплуатационного лимита по RPC.
