## Конкретный дефект в pinning pool key

`prepareSwap` читает `manager.poolIdToPoolKey(profile.poolId)` и сверяет **прочитанный** key с id. Затем quoter и `transaction()` получают **другой объект** — `profile.poolKey`. Равенства `hash(profile.poolKey)===profile.poolId` или сравнения с прочитанным key нет. Адресный synthetic test: manager вернул исходный правильный key, у `profile.poolKey` изменён только fee `90→100`, quoter/router fixtures принимают другой key — функция вернула `prepared`, хотя hash используемого key уже `0x8b3e…ce8af` вместо pinned `0xdde1…9d4cf`. На живой сети при существующем другом USDG/WETH pool это позволяет подготовить quote/swap для иного fee/pool, одновременно показывая liquidity от pinned pool. Исполнимость на том другом pool этим тестом не доказана; несогласованность входов доказана.

Узкий фикс до sender: сверять `profile.poolKey` с key, прочитанным на том же blockTag, и его hash с `profile.poolId` **до quote**, либо передавать только сверенный onchain key и отдельно проверить его поля против pinned tokens/manager/fee/hooks. Адресный отрицательный тест должен подменять лишь локальный key при неизменном ответе manager; существующий mock возвращает сам `profile.poolKey`, поэтому эту ошибку не видит. Никакого нового oracle для этого не требуется.

## Следующий ограниченный пакет

1. Закрыть key consistency и тест выше. Держать один pinned market/slot1, действующие 90/5/5 и закрытый public gate.
2. Под одним **main lock** и одним ops signer/nonce сделать конечные durable стадии `USDG approve → Permit2 approve → swap+unwrap → measured ETH → existing refill`. На каждой стадии сохранять intent до send, hash после send, сверять receipt/nonce/allowance/balances при restart. Расширить диспетчер `resolved()` для ops intent: сейчас неизвестный ему `state.pending` проверяется как транзакция executor, а не source. Unknown hash не повторять автоматически; known hash сверять, запретить второй send на том же nonce. После approval снова вызывать fresh `prepareSwap` и отправлять только проверенный payload.
3. Проверить bootstrap-петлю на реальном потоке денег. Сегодня `infinity-worker` вызывает `collector.pull/pay` **от executor**. Если executor пуст, ops EOA имеет лишь USDG credit в collector, а на кошельке USDG=0, текущий refill не может добыть ETH из этого credit: нужно внешнее пополнение либо отдельное permissionless `pay(slot1)` (при необходимости `pull`) за seed ETH ops signer, под тем же ops journal/nonce. Не закладывать обещание самозапуска из нулевого ETH; зафиксировать конкретную последовательность `credit → ops wallet USDG → swap → refill → старые обязательства` и тест executor=0, ops с ограниченным seed ETH. Сначала разрешать уже оплаченный USDG у ops, затем отдельной стадией автоматизировать сбор credit, если он нужен для автономного пути.

Критерий завершения пакета — после process death на каждой отправляющей стадии нет второго расхода, balance/allowances сверены, swap даёт измеренный ETH на pinned slot1, refill продолжает прежний journal, а отсутствие ETH/ликвидности оставляет понятное ожидание. Это не открывает публичные отправки: source/immutable audit, production caps и real RPC остаются отдельными release gates.
