# Постоянный ответ GPT — reward checkpoint

29.09.2026. Статический review `d2077db`: прочитал diff checkpoint, vault mutations/events, API coverage, тестовые сценарии и эксплуатационные границы. Тесты/build/fork не запускал.

Инкрементальная логика в просмотренном пути согласована с vault. Поля `draws` и `reward` здесь меняются при reserve, finalize/settle и claim; эти переходы выдают учитываемые `DrawReserved`, `RewardAssigned`, `DrawFinalized`, `RewardPaid`. Старый checkpoint наследуется только при совпадении vault и hash его блока на текущей ветке. Хвост событий обновляет проекцию; storage на новом blockTag перечитывается для каждого затронутого draw и адреса награды. Поздний Claim старого приза снова проверяет его draw и reward. Статус `paid` по-прежнему требует `RewardPaid` и нулевой долг, а не только значение storage. При reorg или старом snapshot идёт полный пересчёт; при ошибке прежний хороший снимок остаётся. Конкретного нового пути к ложному `paid` не нашёл.

Поправка к моему прошлому замечанию о нагрузке закрыта **именно для historical storage calls в обычном продолжении**: показанная модель 120 draws/1200 rewards даёт 1320 вызовов при первичной проверке, ноль при пустом продолжении, два при позднем Claim и полный объём при audit/reorg. Это подсчёт mock-вызовов, не измерение реального RPC. Coverage `vault-events-and-checkpointed-storage` честно обозначает, что старые записи не перечитываются на каждом blockTag. Ручной `audit` с существующим STATE принудительно перепроверяет все storage записи до обработанной высоты; для независимого чтения самой истории всё ещё нужен новый STATE и RPC.

Остался **другой** предел постоянного сервиса: `scanWithRpc` и BUY/lifecycle replay каждый раз проходят всю сохранённую историю, API также пересчитывает её при каждом запросе, а state записывает большой JSON. Checkpoint не делает этот путь инкрементальным. Перед публичным сервисом нужны измерения на реалистичной длине истории и нагрузке запросов, затем решение по хранению/чтению без потери полной перепроверки и rollback. Не требуется новый раунд изменения призовой математики.

Операционная предпосылка checkpoint — закреплённый неизменный runtime vault, полная история с начала резервов и один доверенный writer state. Checksum защищает от случайной порчи, не от подмены оператором; API по-прежнему отдаёт локальное наблюдение с высотой/возрастом, не гарантию финальности. Public sends остаются закрыты. Следующий разумный шаг — реальный performance/service прогон и UI на уже определённых состояниях, параллельно с actual admitted Infinity/RPC qualification.
