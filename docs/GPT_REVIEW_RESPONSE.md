## Четыре вещи, которые стоит предусмотреть, когда нагрузка действительно потребует перехода

1. **Не плодить фрагмент на каждую покупку.** В прототипе `append(dir,1)` создаёт новый файл и переписывает весь manifest: `scripts/experiments/segmented-history.cjs` (`append/store/publish`). Seed 5 млн строк имеет лишь 500 фрагментов, потому что пишет партиями по 10 тыс.; серия из 5 млн одиночных append дала бы до 5 млн файлов и O(числа append) manifest, а не нынешние 93 KB. Оговорка об этом есть в плане, но это главный риск неверной экстраполяции результата. Будущий дизайн должен иметь ограниченное число фрагментов при частом append: заполняемый/версионированный tail или партии с проверяемым commit boundary, плюс compaction только с учётом живых readers/backups. Критерий: проверить миллион **одиночных** append или репрезентативные малые batch, построить график файлов, размера каталога, p95 append и restore; отсутствие линейного числа файлов на BUY важнее красивого tail100 на seed.

2. **Разделить «быстрый хвост» и полноту проверки без потери доверия.** Сейчас API проверяет собственный BUY-prefix в памяти, но холодный запуск, lifecycle, координатор и запись всё ещё O(history). Фрагменты снижают I/O только при условии, что индекс по wallet/draw, lifecycle checkpoint, все tx identities, head/branch и независимый replay имеют свои строгие правила. При старте/миграции обязательна полная проверка либо проверенный checkpoint с зафиксированным evidence commitment и понятным периодическим audit. Одна SHA каждого фрагмента доказывает, что прочитанные байты не изменились, а не что в них правильные билеты. Старые сегменты, которые tail не читает, могут испортиться незаметно до audit — это нормальная модель только при запланированной проверке/restore, не «хвост здоров, значит всё здорово». Сверять `ledgerHash`, carry, OPEN/FROZEN/CONSUMED, assigned/paid и контрактные обязательства после каждой миграционной границы.

3. **Публиковать согласованное поколение, а не просто новый manifest.** Прототип правильно игнорирует orphan до publish и допускает возврат старого manifest. В рабочем состоянии это одновременно риск отката: прежняя версия каталога может выглядеть внутренне целой, хотя после неё были приняты BUY, заморожены попытки или отправлены деньги. Каталог должен связывать `chainId/anchor/manifest policy/replay revision/head/hash`, идентификаторы evidence fragments и состояния потребителей. На restore проверять canonical RPC и on-chain commitments, не позволять старому backup затереть новые journals/обязательства. Для crash durability явно проверить fsync файлов **и публикации каталога/директории** на целевой FS: нынешний прототип тестирует исключение до rename, не внезапное отключение машины. Если на целевой платформе гарантии отличаются, документировать процедуру восстановления, а не предполагать одинаковую POSIX семантику на Windows/Linux.

4. **Мерить три оси отдельно.** Блоков/покупок в истории, скорость новых BUY и конкурентные API readers создают разную нагрузку. Следующий тестовый пакет логично оставить смешанным: curve/v4/0x/EntryPoint в поддержанных формах, несколько draws с freeze/consume и paid, reorg, writer + API + coordinator, медленный RPC и восстановление копии на другом пути с денежными journals. Отчёт по изолированным процессам и длительному p95/RSS/диску (не общий peak RSS генератора mock-цепочки). Это даст основание выбрать первое узкое улучшение: consumer lifecycle, формат evidence или индексы; БД не является предрешённым ответом.

## Практическая очередность

Закрыть запланированные mixed lifecycle и полный backup/restore нынешнего формата; зафиксировать измеримый бюджет допустимого простоя и целевое железо. Наблюдать размер снимка, скорость его роста, время cold/append/idle, backlog, API cold/refresh и свободное место под backup. Если бюджет начинает систематически нарушаться, сделать **один** пилот хранения на копии реальной evidence с одиночными append/reorg/freeze и независимым replay; переключение writer проводить только после сравнения обязательств на фиксированной высоте. Нет нужды строить кластер, шардирование или менять продуктовые правила сейчас.

Ни один из результатов 5 млн синтетических строк сам по себе не является блокером тестового релиза или подтверждением бесконечного масштаба. Особенно не использовать его как оценку стоимости 5 млн on-chain покупок.
