## Контрактная граница

Конкретного обхода notice/id/version и balance constraints в текущем коде не нашёл. Один pending без overwrite; отмена доступна лишь immutable publisher, новое объявление получает новый id и полную задержку. Permissionless activation сверяет тот же codeHash и assets, не обращаясь к старому сломанному adapter. `expectedVersion` останавливает queued convert после смены маршрута. Перед swap снова проверяются runtime и assets, а allowance выдаётся ровно на amount, сбрасывается после успеха; фактические TOKEN debit и USDG credit сверяются по балансам. Revert откатывает allowance и accounting. USDG forwarding сохраняет immutable destination и работает при отказе adapter или oracle. Старый LocalPrizeConverter/его inventory сюда не мигрирует.

`minimumOutput` действительно вычисляется контрактом из ratio, возраста наблюдения и immutable slippage с округлением вверх. **Это проверка выполнения заявленной цены, а не происхождения цены.** Любой может вызвать `convert` в выгодный ему момент, пока опубликованное значение не старше `maxPriceAge`; при быстром падении неликвидного TOKEN даже формально свежий курс может плохо описывать текущую исполнимую цену. Publisher управляет выбором adapter и может мешать заменам, но не может сменить source или призовой адрес через этот ABI. Timelock даёт время увидеть вредное объявление, не делает adapter добросовестным. Прокси/внешние зависимости за неизменным runtime hash и рыночная цена остаются trust boundaries. Это не основание сейчас усложнять state machine; рабочему worker всё ещё нужен новый ABI с `expectedVersion` и реакцией на stale version.

## Цена для молодого TOKEN

Практический порядок выбора перед deployment:

1. Проверить, существует ли **реальный TOKEN/USDG feed** у независимого провайдера или иной глубокий независимый рынок TOKEN, и на этой сети, с доступными on-chain обновлениями. Для нового meme TOKEN это нельзя предположить заранее. PAIR `PairPriceOracle` в документации описан как registry цен ETH/Stock Tokens для launch; наличие его feed не доказывает feed нашего TOKEN. Chainlink также требует отдельно оценивать ликвидность и устойчивость цены нового актива ([PAIR docs](https://pair.fund/docs), [Chainlink feed selection](https://docs.chain.link/data-feeds/selecting-data-feeds)).
2. Если такой опоры нет, проверить, умеет ли **конкретный установленный hook** хранить наблюдения и даёт ли пул достаточно длительную, дорогую для манипуляции историю. v4 не предоставляет встроенный TWAP; hook может добавить oracle behavior, но наличие hook само этого не доказывает ([Uniswap oracle docs](https://developers.uniswap.org/docs/protocols/v3/concepts/price-oracles), [v4 hooks](https://developers.uniswap.org/docs/get-started/concepts/hooks)). TWAP того же тонкого пула сглаживает разовую атаку, но не является экономически независимой ценой: длительная манипуляция/редкие сделки и малая ликвидность остаются. Нужны минимальное окно наблюдений, измерение глубины относительно `maxInput` и предел отклонения; если данных мало — ждать, не продавать.
3. Автоматический signed reporter/committee возможен, если нет рыночного feed, но это **новая власть над ценой**, даже если update отправляет бот, а не человек. Нужны наблюдаемые источники, несколько независимых подписантов, сроки/ограничения и честное решение владельца о доверии. В рамках этого review такой механизм не утверждён.

Доступность нельзя лечить молчаливой заменой immutable `priceSource` на spot или отключением minOut. Нынешний fail-closed режим оставляет TOKEN ждать, а уже полученный USDG отправляет в vault. Если необратимый отказ source неприемлем, это отдельное **продуктовое решение до deployment**: заранее определённые независимые fallback feeds в неизменном source либо явно опубликованная и задержанная власть менять ценовую политику. Второй вариант расширяет доверие сильнее, чем замена swap adapter; обещать его безопасность текущим пакетом нельзя. Без пригодной цены технически честный ответ — не делать swap.
