## Bloom/replay: вывод по безопасности билетов

Подтверждённого пути **тихо пропустить подходящий BUY** в новом коде не нашёл. `pons-bloom-evidence.cjs` RLP-кодирует фактический 16-польный header и требует Keccak=block hash; omission хранит этот header, сверяет hash/parent/number/time и отрицательный bloom. `direct-buy.cjs` отдельно проверяет непрерывность ветки и отсутствие BUY-событий для manifest, `attempt-lifecycle.cjs` — события источников/vault, `reward-observation.cjs` — vault. Поэтому пустой локальный массив transactions сам по себе не основание для нулевых билетов/наград. Это доказательство относительно **доверенного canonical/finalized RPC**, не независимая проверка консенсуса.

При positive bloom `replay-direct-buy.cjs` читает полные tx и receipts, проверяет число, индексы, hash и ветку; `direct-buy.cjs` затем проверяет provenance каждого лога, непрерывные logIndex и декодирует те же точные маршруты. False positive увеличит работу, но не выдаст билет. Parent code у self-batch/EntryPoint читается только у candidate и на предыдущей высоте. Версионированная Pons смена token/curve через policy здесь не скрыта: имеющаяся `buyPolicyHistory` допускает extension только `direct-buy-v2` без изменения прочих полей; неподтверждённый новый Pons маршрут должен оставаться unsupported. При появлении иного Pons versioning scanner и bloom watched-set потребуется пересмотреть вместе с policy.

`bounded-map.cjs` ждёт все уже начатые работы и лишь затем возвращает ошибку; `indexOnce` выходит из locked state после этого. Cache для receipt привязан к его собственному blockNumber и при rollback не должен пережить удалённую ветку. Старые checkpoints инвалидированы `REPLAY_REVISION`. Отдельная актуальная проблема остаётся: **короткие сравнения 10 блоков и 135 tests не доказывают эквивалентность каждого реального BUY**; server4100 независимый replay проверяет сохранённую историю, но использует те же правила omission. Полный receipt reader на адресных интервалах и адресная сверка известных live покупок остаются полезным контролем при catch-up, без объявления unsupported 47 routes билетами.

## Обязательные ворота до финансовой автоматики

1. **Фактически догнать finalized**, сверить независимым чтением несколько реальных BUY и обе проекции API, проверить `caughtUp`, freshness и стабильное отставание на длительном интервале. На опубликованном evidence: server8100 блоков, lag22341, `catchingUp`; 43.15s/1000 и отдельные50.55s/1000 — хорошие локальные скорости, но не доказанный устойчивый steady state. Не повышать timeout/freshness и не переключать публичный кабинет, пока он показывает неполную историю.
2. **Разбить каждый `eth_getLogs` по допустимому окну с проверкой целостности**, не только индексатор. `scripts/pons-automation.cjs` → `claims()` вызывает `queryFilter(AttemptsConsumed,from,to)` до **1000 блоков**: на наблюдавшемся Free RPC лимите10 это остановит проход до выплаты, причём catch-up payout cursor после запуска особенно уязвим. Минимально порции ≤10, последовательное сохранение cursor только после проверенного полного окна, проверка hash граничных блоков и fault test «сбой в середине, restart без пропуска и дубля». `scripts/buy-policy-admission.cjs` при `publishedCount>0` также читает notices от anchor одним запросом: разбить и проверить count/order/commitment; нулевая оптимизация не решает будущий первый notice. Не возвращать пустой logs при ошибке.
3. **Оценить рост state до включения долгой службы.** Evidence:24.83MB после8100 блоков, то есть ~3.1kB/блок на данном участке. При10 блоках/с это условно ~2.65GB/сутки, ещё до роста tx/истории и резервных копий; прежние35GB свободного диска сервера не дают большого горизонта. Это экстраполяция, а не предсказание точного размера. Зафиксировать 6–24ч измерение размера, времени save/cold replay, RPC usage и свободного диска; поставить disk/lag alert и **проверенную границу хранения**. Ближайшая инженерная идея: выносить старые hash-bound omission headers в проверяемые сегменты/архив с checkpoint и recovery-тестом, не отбрасывать доказательство отсутствия и не переписывать сразу всё в БД. Пока такой границы нет, рост не следует называть решённым.

Это конкретные эксплуатационные блокеры включения, а не предложение отложить запуск на «архитектуру мирового масштаба». Financial service может остаться выключенным, пока индекс и RPC не способны обслужить и новых покупателей, и уже назначенные выплаты.

## Скрин GeckoTerminal: «Open Source: NO»

Здесь два разных смысла. GitHub репозиторий `Marapu1a/rh_project` **уже public**, но в корне нет `LICENSE`. Это публично читаемый код, однако без явной лицензии нельзя корректно назвать весь проект предоставленным для свободного использования. При этом GoPlus `is_open_source=0` касается **контракта TOKEN по адресу `0x6EA39A23AA46E51CA6CD2d1cbc0B5bfb29ECB216`**, а не видимости нашего GitHub. У GoPlus при таком ответе ряд остальных признаков может быть пустым/«?». Дата нового листинга, pool/holders/transactions и недостающие соцссылки тоже влияют на GT Score; публикация исходников не обещает автоматически высокий балл. [GoPlus fields](https://docs.gopluslabs.io/reference/response-details), [GT score](https://support.coingecko.com/hc/en-us/articles/38381394237593-What-is-the-GT-Score-How-is-the-GT-Score-calculated).

**Первое адресное действие:** верифицировать именно deployed QIANQI token на поддерживаемом explorer/Sourcify и получить публичную ссылку на результат; повторить GoPlus запрос, дать агрегаторам время обновить данные и проверить поля именно этого адреса. Для launcher-generated Pons token исходник/компилятор могут принадлежать сборке Pons: использовать настоящий standard JSON input, версии/настройки, исходники зависимостей и constructor/immutables. Имеющееся сравнение исполняемого runtime с Harmonic оставило metadata mismatch; не выдавать его за exact verification QIANQI. Sourcify различает exact match и match; если exact недостижим, честно показывать тип совпадения и ask Pons/explorer о metadata, а не подгонять исходник под сканер. [Sourcify verification](https://docs.sourcify.dev/docs/api/), [виды совпадения](https://docs.sourcify.dev/docs/exact-match-vs-match/).

**Второе, отдельное решение владельца:** если хотим полноценный open-source *проект*, проверить всю историю публичного GitHub на ключи/пароли/персональные данные и права на vendor/Pons код, определить объём публикации, добавить согласованную лицензию для собственного кода (например MIT/Apache-2.0 после проверки совместимости), понятный README с адресами/границами/сборкой и пометки чужих компонентов. Простое добавление LICENSE не верифицирует on-chain bytecode и не исправляет старые секреты в истории. Переводить visibility уже нечего; публикация всего текущего операционного дерева как «готового аудита» была бы неверным сигналом. [GitHub о лицензии](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository), [об истории и секретах](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## Приоритет

Сначала безопасный catch-up + `getLogs` порции + подтверждённый источник TOKEN; затем контролируемое включение с реальными health/диском/газом. Маркетинговый GT score сам по себе не критерий безопасности и не оправдание включить выплаты при неполной истории.
