## Вердикт

В проверенном локальном пути `request(context)` вызывается атомарно из seal, сохраняет единственный будущий round и уникальный id; изменить round/context/consumer через API нельзя. `prove` проверяет подпись закреплённым evmnet BLS ключом и записывает domain-separated seed. Кэш не позволяет принять другой proof: подпись проверяется и при повторе, затем seed должен совпасть. `deliver` допускает повтор без нового callback; revert callback откатывает флаг доставки, но оставляет уже proven seed в предыдущей транзакции. ReentrancyGuard и проверка фиксированного provider на стороне контроллеров закрывают очевидные повторы. В адресной интеграции оба контроллера дошли до settlement и claim, повторный claim отклонён; no-win отдельно оставил резерв свободным. Подтверждённой возможности выбрать второй результат или заплатить дважды в этих путях не нашёл.

**Конкретная граница в коде:** `drandPreflight` при `PROFILE()` → `CALL_EXCEPTION` без данных возвращает `null`, а оба executor трактуют `null` как разрешение идти к seal. Это нужно для старых local fixtures, но на публичной сети отсутствие `PROFILE()` является обходом всей проверки свежести. Сейчас production admission и deployment ещё не реализованы, поэтому это не доказанный дефект уже работающего публичного сервиса. Перед подключением публичного deployment сделать fallback явно `chainId === 31337` плюс разрешённый fixture/pin; во всех других случаях fail closed и отдельный тест для отсутствующего/неизвестного profile. Одной только пометки в документации недостаточно для будущего запуска.

Операционная проверка корректно названа наблюдением, а не гарантией: часы сервера и `finalized` от RPC могут ошибаться, сеть может измениться после preflight, прямой permissionless seal его обходит. Тестовый lead 3600 с и лимиты не являются production параметрами. Не обещать, что выбор round невозможно сместить при глубоком reorg; это принятая владельцем граница MVP. `ready()` тоже только структурный сигнал. Публичный deployment, source pins, газ полного цикла и непрерывный delivery пока не подтверждены.

## Следующий шаг

Делать узкий **delivery worker** для уже закреплённых requests: получать именно сохранённый round, проверять подпись локально/на adapter, затем `prove`/`deliver` с существующим журналом отправок, сверкой known hash и unknown-send stop. Не запускать новый RNG journal и не заставлять preflight для новых freezes блокировать доставку старого proven request. Проверить задержку или недоступность drand, callback revert, restart и повторную доставку; ожидание не даёт права заменить round. После этого один сквозной Infinity BUY → dataset → drand → settlement → USDG в кошельке, с реальным источником бюджета и без смешения fixture funding с выручкой. До публичного запуска отдельно закрыть fail-open profile, finality/deployment admission и утверждение экономических долей.
