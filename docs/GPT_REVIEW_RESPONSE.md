# Постоянный ответ GPT — wallet rewards и цена постоянного наблюдения

29.09.2026. Статический review `209e96b..07a8ab2`: прочитал API/проекцию vault, indexer, историю событий и storage PromoVault, адресные сценарии и документацию. Tests/build/fork по договорённости не запускал.

## Корректность пользовательского статуса

В просмотренном пути прежнее замечание про policy/cache reorg закрыто адресным сценарием: после смены ветки сохранённый, ещё не начатый Short job получает policy mismatch без отправки и без переписывания artifact. Wallet API пересчитывает lifecycle по сохранённым blocks: `open` и `consumed` не берутся из простого minted total. Отсутствие decoder-кандидата честно не трактуется как отказ любой произвольной покупке.

`projectRewards` берёт логи только из закреплённого vault; reserve → assignment → finalized → paid связаны drawId, wallet, asset и суммой. Paid возникает только после успешного `RewardPaid` и ещё проверяется совпадением `draws.paid` и нулевого `reward(drawId,winner)` на blockTag снимка. Нулевой storage без события не превращается в выплату; неполная или несогласованная история останавливает новый снимок. При RPC/storage error сохраняется предыдущий хороший снимок, API помечает его stale. Старые снимки без reward section дают `rewards:null`, а не «приза нет». Здесь ложного раннего paid не увидел. Это доказательство accounting данного vault на наблюдаемой ветке, не проверка справедливости выбора победителя.

## Главный практический риск перед постоянным сервисом

`observeRewards` на **каждом** проходе делает исторический `eth_call draws` по каждому прежнему draw и `eth_call reward` по каждой прежней награде. При максимально частом Short (раз в 6 часов) и десяти победителях за 30 суток накопится около 120 draws и 1200 rewards: это порядка **1320 исторических eth_call на один проход**, не считая чтения блоков/BUY/policy. При idle poll раз в 10 секунд получилось бы около 11 млн таких запросов за сутки. Реальная частота и число победителей будут зависеть от готовности/участников, но рост линейный без верхней границы. Это не дефект выплаты и не причина менять призовую логику; это конкретная причина пока **не считать watch production service** даже при хорошем archive RPC. Замер одного маленького fixture не покажет этот предел.

Следующий ограниченный инженерный шаг: определить нагрузочный бюджет для возраста истории и победителей, затем сохранять проверенный checkpoint accounting и читать новые reserve/assignment/pay инкрементально, с rollback при reorg и возможностью полного независимого аудита. Не ослаблять правило «paid только после события + storage». Пока этой границы нет, хотя бы явно ограничить режим/частоту и смотреть на длину прохода, квоты RPC и лаг относительно finalized.

API слушает loopback, не имеет signer/Claim и правильно разделяет `observed` (возраст локального снимка) от сетевой финальности. В будущем UI стоит показывать `targetBlock` и `indexerState` рядом с возрастом: свежий по времени `catchingUp` снимок может всё ещё сильно отставать от сети. Глобальные draws/no-winner и live Infinity admitted история остаются отдельными задачами. Public sends закрыты.
