## Вердикт

Это уже связанный локальный путь, а не один mock loader. Реальный `BuyPolicySource`
сверяет publisher через `msg.sender`, последовательность hashes, bytes и notice;
admission сравнивает все логи с `publishedCount/currentHash/lastFromBlock` на
finalized checkpoint. Пропуск последнего лога теперь обнаруживается. Сквозной
тест действительно отправляет транзакцию, проводит новый BUY и сохраняет старые
frozen Short/Monthly. Разделение live execution и finalized cutoff разумно.
Тестовый контрактный publisher подтверждает именно вызов через контракт, не
свойства конкретного Safe. Старые snapshots не переписаны.

**До публичного запуска остаются два блокера этой цепочки и один важный предел
тестового утверждения:**

1. Авторизованный `announce` может записать любые bytes с правильным hash.
   Невалидный route/JSON становится неснимаемой записью: loader отвергает её
   при каждом дальнейшем replay, а контракт не имеет исправления. Dry-run
   защищает штатный CLI, но не прямой вызов ключом/Safe. Для регулярных денежных
   draws это риск полной остановки. Я бы не принимал его как релизную норму.
   Целостное решение: убрать произвольный JSON из полномочия объявителя. Source
   публикует только типизированное, ограниченное изменение из набора уже
   проверенных adapters (для этого MVP — один новый route и будущий fromBlock),
   сам проверяет допустимый id/порядок/notice и хранит commitment; verifier
   детерминированно собирает полный manifest из доверенного genesis и такого
   события. Если нужно новое поколение adapter/schema, его вводят отдельным
   публичным source/deployment решением, не скрытым setter/skip. Исторические
   BUY и frozen остаются привязаны к прежней версии. До выбора этого дизайна
   не подключать публичные средства к текущему произвольному announce.
2. RPC CLI допускает отсутствие `buyPolicy`: `resolveBuyPolicy({manifest: v2},
   rpc, cutoff)` возвращает v2 вообще без RPC/admission. Я воспроизвёл это с
   новым route `fromBlock: 1`: результат `admitted: false`, route принят.
   Для нового экземпляра v2 genesis может быть осознанным выбором, но сейчас
   режимы не различаются в выводе. CLI/публикуемые ledger и dataset verifier
   должны требовать закреплённый deployment trust для заявленного public
   instance либо явно маркировать результат как unadmitted/offline. Удаление
   `buyPolicy` из JSON не должно превращать проверку опубликованной истории в
   обычный genesis-ввод без заметного изменения режима.
3. Тест «persisted forgery» меняет только `snapshot.domain.buyManifestHash`.
   Scheduler сравнивает этот hash с политикой, а `validateJob` сверяет
   самосогласованные checksum/root/snapshot. Это не сверка участников и количества
   попыток сохранённого job с независимым BUY replay на его cutoff. Согласованно
   переписанный artifact и его checksums пройдут эти проверки. Это не новый
   обход контракта policy source, но нельзя называть его защитой от подмены
   persisted dataset; перед первым begin нужен replay сохранённого cutoff
   или отдельный обязательный независимый verifier (`closeEmpty` уже перестраивает
   artifact из истории). Уже начатый on-chain job
   восстанавливать по его commitment, не заменять artifact молча.

Ближайший пакет я бы ограничил **первым блокером и честной границей trust в CLI**;
затем проверил восстановление сохранённых jobs. Независимо от этого до релиза
остаются реальные финальность сети, полномочия/ключи, notice, PAIR venue и RNG:
локальные тесты chain31337 этих решений не принимают.
