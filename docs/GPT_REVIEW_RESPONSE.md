# Постоянный ответ GPT — wallet API cache и worker

29.09.2026. Статический review `56ccf3e..948f6c6`: прочитал подготовку снимка, thread/HTTP границу, условия смены поколений, индексерные метрики, тесты и документацию. Tests/build/fork не запускал.

В просмотренном коде не нашёл нового пути к ложному `observed`, нулевому балансу вместо ошибки или потере проверки reward. Новая версия файла допускается в prepared Maps только после checksum/config/admitted policy, полного BUY+lifecycle replay и сравнения проекции событий наград с сохранённым снимком. Generation проверяется до/после чтения и после подготовки; невалидная замена сбрасывает кэш и даёт `unavailable`, waiting/stale считаются по времени исходного успешного снимка. Возвращаемые объекты изолированы от Maps через clone. Внешний HTTP endpoint получает только ответ выбранного кошелька; парсинг и replay целой истории выполняются в worker.

У worker разумная граница отказов: max64 pending, timeout30s, поздние сообщения прежнего worker отбрасываются после `stop`, все ожидающие завершаются как unavailable; следующий запрос может поднять новый worker. `close` запрещает возобновление. Асинхронный stat в main перед ответом отбрасывает поколение, сменившееся во время доставки. Это не транзакционная гарантия, что файл не поменяется сразу **после** stat, и документация такого не обещает. Подтверждённого в этом пакете race-багa не увидел.

Измерения полезно читать буквально: синтетические 5013 блоков и 9.59 MB — cold worker ≈868 ms при max gap основного таймера ≈16 ms; warm ≈0.27 ms для известного кошелька. Изоляция снимает блокировку HTTP event loop, но не ускоряет indexer scan, полный BUY/lifecycle replay при смене файла или JSON-запись. При частых новых снимках и длинной реальной истории это может давать очередь/timeout и 503; данный benchmark этого не опровергает. `state.status.metrics` фиксирует scan/replay/reward/lag и возвращает save/total/bytes, так что для следующего шага уже есть точки измерения.

Следующий ограниченный шаг поддерживаю: постоянный service/runbook с одним writer, восстановлением после потери RPC/worker и понятным статусом stale/unavailable; затем **реальный admitted Infinity** замер задержки indexer, частоты смены snapshots, cold/reload API и нагрузки известных кошельков. Не надо на основании warm synthetic numbers объявлять production readiness или переписывать хранение до измерения. Public sends, signing и сайт остаются отдельными воротами.
