# PAIR: восстановление fork, экономика и интеграция

Дата: 12.09.2026. **Все четыре экономических сценария и интеграция rollover + PromoVault прошли.** Эксперимент целиком локальный; публичные транзакции и реальные расходы отсутствуют. Размеры наград не выбирались.

Последующее исследование: [offline farming-модель](FARMING_RESEARCH_2026-09-12.md) проверяет 10 368 комбинаций бюджетов и entries на основе этих измерений. Найдены условно прибыльные сценарии; исполнение атаки с выдачей и продажей TOKEN-призов на fork остаётся следующим этапом.

## Почему раньше ломался launch

Трассировка локального fork показала: неизменившийся proxy implementation теперь направляет launch через новый coordinator/registry/factory. Проверка salt только по старой фабрике была недостаточной.

- Launchpad implementation: `0x8000b64b62837a1511e302c62354e1bc39b5641a`.
- Фактически вызванный coordinator: `0xddc69cbfb38f3f24d23b980c9e156c62a431687b`.
- Mode registry на этом пути: `0x34b34d3f409c562ff2d16f211f516e30695b3809`.
- Фабрика: `0xa1ff181f6cd1f84a36385df37e8080566d25235f`.
- Новый salt: `0x0000000000000000000000000000000000000000000000000000002f2c72cdcd`.
- Предсказанный/созданный локально TOKEN: `0xa927cb8a225e2fa3300e9ff5f60921c2d9065555`.

После подбора salt по фактической фабрике успешны read-only launch с buy 0,00001 ETH и без buy. Текущий frontend bundle `index-BwhDsANA.js` содержит те же новые адреса; локальная трассировка независимо показала вызовы этих адресов. Это объясняет прежний InvalidLaunch, а не доказывает совместимость произвольных будущих PAIR upgrades.

Исторический блок прежней проверки недоступен через основной public RPC; альтернативный BlockReq ограничивает публичную историю последними 32768 блоками. Поэтому эксперимент использует свежий fork. Для контроля нагрузки добавлен локальный read-only HTTP посредник: последовательные запросы, временный кеш неизменяемых чтений и ограниченные retries. Он не подставляет фиктивное состояние при ошибках. В завершённом прогоне: 513 upstream requests, 0 retries, 0 JSON-RPC errors после применения ограничителя. Временный listener закрывается после выполнения.

Evidence: [trace](../research/local-launch-trace.json), [текущая launch simulation](../research/current-launch-2026-09-12.json), [RPC probes](../research/rpc-recovery-2026-09-12.json).

## Условия измерения

- Fork block `0x3a4215b`, исходная сеть Robinhood mainnet 4663, локальное исполнение Hardhat 31337 / Cancun.
- Новый single-pool TOKEN/USDG, созданный настоящим PAIR на fork. Pool ID `0x4748a39272f4589631e9e64b1fa5d2c1047c37524bd48d0c6a540780c01fa6e0`, fee 10000, tickSpacing 200, hook `0x438b86c71840c3b4df3f839aed6bb889e2d780c0`.
- Начальный developer buy 0,00001 ETH. Его комиссии собраны отдельно и исключены из экономических сценариев; для entries он также исключён.
- Перед каждой строкой таблицы состояние возвращено к одному и тому же snapshot. Внутри пяти циклов состояние последовательно меняется.
- Тестовый участник получает 10000 USDG через локальную замену только собственного ERC20 balance slot. Это синтетический стартовый капитал, не on-chain mint. Pool reserves, TOKEN supply, цены и логика PAIR не подменялись.
- Все BUY/SELL проходят через настоящий PoolManager и hook. Тестовый SwapFixture обеспечивает transferFrom от участника и получение выхода тем же участником. Это не штатный UniversalRouter/UI.
- Условие расчёта долларового объёма: **1 USDG = $1**. Рыночная привязка USDG отдельно не измерялась.
- Entries в таблице — гипотетический результат накопленного gross BUY / 100 USDG, если кошелёк и маршрут допустимы. Реальной регистрации Promo и indexer ещё нет; тестовый helper не объявляется автоматически поддержанным маршрутом.

На BUY 100 PoolManager передал PAIR vault 999999 raw USDG LP fees; 300000 raw ушло на protocol address `0xbc27542ae2ed2e4d1d380b5fe8b2d48404fd824c`, а 699999 raw получил наш router. На обратном SELL gross TOKEN fees составили 287151708606117612246364 raw, из них 86145512581835283673910 raw ушло protocol и 201006196024282328572454 raw — creator. Это подтверждает 70/30 с целочисленным округлением на текущем исследованном пути. Это не универсальная политика всех PAIR-веток.

## Цена и размер сделки

Начальная spot-цена: примерно `0,000003348654174815 USDG/TOKEN`.

| BUY | Средняя цена покупки выше начальной spot, включая fee | Рост spot после BUY |
|---|---:|---:|
| 25 USDG | 1,7567% | 1,4837% |
| 100 USDG | 3,9964% | 6,0003% |
| 500 USDG | 15,9416% | 31,7495% |

Первый столбец объединяет комиссию и движение по кривой; это не изолированная оценка slippage. Spot после обратной продажи тоже не обязан точно совпасть с исходной. Цифры относятся к свежему тестовому рынку с этой стартовой конфигурацией, а не к любой будущей ликвидности.

Крупный цикл оказался дешевле в пересчёте на entry: 1,8636156 USDG против 1,961864 USDG у пяти небольших циклов, без gas. Разбиение покупок не даёт дополнительных entries, но стоимость торговли и gas от размера/последовательности зависят. Нельзя закладывать единственную постоянную «цену entry» по одному сценарию.

## Что можно сказать про farming

До наград все исследованные циклы убыточны. **Это ещё не доказательство отрицательного EV после наград.**

Для атакующего, получившего доли `f_short` и `f_month` соответствующих entries, при симметричной модели наград:

```text
ожидаемая прибыль =
  f_short × исполнимая USDG-стоимость коротких призов
  + f_month × USDG jackpot
  - торговые потери
  - gas
```

Вероятность «примерно 1/3 entries выигрывает» сама по себе не ограничивает выплату: важны размер призов и общий бюджет. Доли короткого и месячного набора entries могут различаться.

В измеренном цикле 500 USDG атакующий получает 5 условных entries за 9,318078 USDG торговой потери. Если ожидаемая совокупная выплата этим entries превысит эту потерю плюс gas, цикл станет выгодным. Например, при доле 50% в обоих наборах порог общего исполнимого призового бюджета без gas составляет 18,636156 USDG; при почти полном контроле entries — примерно 9,318078 USDG. Это условные пороги для данного цикла, не предложенные размеры призов.

Органические комиссии и стороннее финансирование могут увеличить бюджет, который пытается захватить атакующий. Поэтому нельзя проверять только возврат его собственных fees. Отдельный adversarial payout simulation с выбранной моделью наград/органическим бюджетом ещё не выполнен: модель наград пока не зафиксирована.

TOKEN revenue — инвентарь, а не готовый USDG-доход. Для окончательного EV нужно оценивать реализацию выигранных TOKEN через рынок, включая новые комиссии и ценовой эффект. Умножение на spot может завысить доступную сумму; эта таблица не делает такой конвертации.

## Gas: предел точности

Таблица показывает локальные EVM gas units только для swap-транзакций. Approvals, запуск, keeper collection/claim, rollover и выдача призов в пользовательскую round-trip цифру не включены. Их receipts сохранены отдельно в полном JSON, но стоимость оператора не приписывается трейдеру.

Не воспроизводятся полноценные Nitro L1 data fees. Штатный UI/UniversalRouter может иметь другой расход gas, чем SwapFixture. ETH/USDG conversion для gas не выполнялась. Поэтому потери без gas — нижняя оценка затрат этого торгового цикла, а не точная будущая сумма списания в кошельке. [Официальное описание gas Robinhood](https://docs.robinhood.com/chain/gas-and-fees/).

## Закрытая интеграционная проверка

Использованы настоящие локально развёрнутые `FeeRouter.sol` и `PromoVault.sol`, реальные PAIR vault/PoolManager и тестовый DrawControllerFixture для задания результата. Последний не становится production controller.

После отдельного BUY/SELL оставлены несобранные комиссии и прямые переводы TOKEN/USDG. Rollover собрал их в старую кампанию, сохранил credits; повторный stale вызов отклонён. Затем деньги выплачены PromoVault, зарезервированы, назначены и получены фиксированным winner через claim. После rollover прямые поступления отнесены к новой кампании, старые totals не изменились.

| Asset | Старый доход и выплаченный приз, raw | Новый распознанный доход, raw |
|---|---:|---:|
| TOKEN | 51357614296187694346764 | 7 |
| USDG | 175193 | 7 |

После claim reserved и claimable PromoVault равны нулю. Проверка использует локальную гипотетическую выдачу 100% доступного бюджета для теста проводки, а не выбранную продуктовую политику наград.

В JSON сохранены 93 успешные транзакции-вызова; локальные constructor deployments выполняются дополнительно. Сценарии разделены snapshots, поэтому это не единая последовательность публичных chain receipts. Исходный historical fork остаётся недоступен, но новая версия rollover и PromoVault теперь проверены вместе с актуальным PAIR на свежем fork.

`npm run test:fork` запускает текущий объединённый эксперимент; `npm run report:economics` строит CSV из сохранённого результата. Исходный `scripts/fork-fee-router.cjs` оставлен для воспроизведения исторического baseline. `RH_RPC_URL` позволяет выбрать другой upstream; по умолчанию используется public BlockReq. Нужен Node с fetch и существующие npm/Python dependencies.

При повторе используется свежий блок и сохранённый проверенный payload новой фабрики; результат может измениться, salt может быть занят или PAIR route может обновиться. Новый успех необходимо проверять, а не предполагать. По умолчанию JSON/CSV текущего эксперимента перезаписываются. RPC cache временный и не гарантирует offline replay после pruning.

Ближайшие продуктовые решения: сформировать кандидаты бюджетной политики и долей органических/атакующих entries, затем проверить совместный EV коротких и месячных наград с исполнимой оценкой TOKEN. Подбор призов и implementation indexer в этот этап не включались.
