# Источник цены TOKEN → USDG: исследование 24.09.2026

Статус: исследование, не выбранный production oracle. Контракты не менялись.
Наш TOKEN ещё не запущен. Проверялся существующий публичный reference PAIR,
а не ликвидность будущего проекта. Предыстория: [converter](SCHEDULED_PRIZE_CONVERTER.md).

## Проверенные факты

В [сохранённом исходнике hook](../research/pair-source-audit/sources/PairV5LaunchV2NativeFeeHook.sol)
есть `consult` и `getQuote`: окно 1800 секунд, максимальная давность 300 секунд,
минимальный интервал записи 60 секунд, кольцо 32 записи.
Исходник совпал по hash с source-audit manifest; runtime публичного hook совпал
с ранее верифицированным runtime hash. Это проверка provenance, не новый аудит PAIR.

[Read-only probe](../research/price-source-probe.cjs) через Blockreq, chain4663,
блок `0x4412069`, hash
`0x63c6c858c7427774fc18ce552307f0dfc1d1fa519a224348bc7d140509d35cc3`:
5 записей, последняя старше timestamp блока на 966392 секунды (около 11.2 суток).
`consult` и `getQuote` вернули `InsufficientHistory()` (`0x1b4ff732`).
[Полные ответы](../research/price-source-probe-2026-09-24.json) сохранены;
hash блока перепроверен после чтений. Транзакций не отправляли. Один RPC —
не независимый консенсус доказательств. Результат не относится ко всем PAIR-пулам.

## Почему готовый hook пока не подходит как единственная защита

`_beforeSwap` записывает старый tick; `_afterSwap` новый tick не записывает.
Затем accumulator взвешивает старую запись вперёд, до следующей записи.
Например, перед сделкой в t=3600 tick=0, после неё tick=10000 и сохраняется
до t=5400. Следующая запись в t=5400 содержит 10000, но consult окна
[3600,5400] возвращает 0. Фактический tick этого промежутка — 10000.
Отношение цен при такой разнице ticks около 2.718; это условный пример,
не утверждение о наблюдавшейся атаке или её стоимости.

[Локальная модель](../research/price-sampling-model.cjs) воспроизводит этот
контрпример, постоянную цену, stale и недостаточную историю. Это source-level
проверка формулы, не EVM replay. Сделки внутри 60 секунд также не обязаны
создавать запись. Окно заканчивается на последней записи, не на текущем блоке.
Свежая запись не доказывает корректность всей истории или глубину ликвидности.
Нельзя исправить это простым wrapper или искусственной сделкой для обновления timestamp.

`getQuote` переводит сумму по tick: fee и price impact конкретного swap не учитывает.
Исторический reference и исполнимая котировка нужны для разных проверок.

## Варианты

| Вариант | Польза | Ограничение / вывод |
| --- | --- | --- |
| Spot / quote того же пула | Проверка ожидаемого исполнения и размера swap | Сдвигается вместе с рынком; не единственная защита от плохого adapter |
| Встроенный PAIR hook | Готовая on-chain история | Найдено расхождение семантики интервалов; не принимать единственным oracle |
| Собственный on-chain sampler | Проверяемые записи, без ручного назначения цены | Газ, bootstrap, пропуски и манипуляция в моменты sampling; не автоматически точный TWAP |
| Автоматический расчёт по полной истории Swap | Можно восстановить post-swap интервалы и проверить replay | On-chain контракт сам не проверяет off-chain историю; подписанный reporter добавляет доверие |
| Независимый внешний feed | Другая инфраструктура и потенциально несколько рынков | Feed нашего TOKEN не установлен; нельзя планировать запуск, предполагая его наличие |

Несколько RPC или подписантов, читающих один пул, не создают несколько независимых
рынков. Для молодых активов недостаток истории и ликвидности остаётся риском даже
с внешним feed: [Chainlink о качестве источников](https://docs.chain.link/data-feeds/selecting-data-feeds).
Проверки давности и качества данных остаются обязательными:
[Pyth best practices](https://docs.pyth.network/price-feeds/core/best-practices).
Есть специальные конструкции oracle hooks, например
[Uniswap truncated oracle](https://blog.uniswap.org/uniswap-v4-truncated-oracle-hook),
но это не доказательство наличия такой защиты в данном PAIR hook.

## Рекомендация и следующий ограниченный шаг

Не подключать PAIR `getQuote` напрямую как обязательный immutable priceSource.
Не выбирать сейчас проценты slippage, минимальную ликвидность или размер сделки
без измерений. Маленький maxInput ограничивает одну операцию, но не суммарную потерю
при повторных вызовах; его недостаточно как единственной защиты.

Следующий шаг — локальный replay post-swap истории на reference и сравнение
с hook: спокойный рынок, редкие сделки, резкий скачок, отсутствие истории/ликвидности.
Одновременно проверить, какой объём TOKEN реально продаётся при выбранном ограничении
impact с учётом fee. Итог — выбрать между собственным sampler и явно доверенным
автоматическим reporter, либо другой моделью исполнения. Это отдельное решение,
а не уже согласованное расширение полномочий. Не строить все варианты сразу.

При отсутствии пригодной цены TOKEN-конвертация ждёт. Уже полученный USDG может
продолжать идти в vault через независимый forwardQuote; frozen/claimable не затрагиваются.
Immutable priceSource — реальная граница: его отказ не лечится заменой swap adapter.
До deployment нужно принять эту зависимость или отдельно пересмотреть модель.

Проверки: `node research/price-source-probe.cjs <new-output.json>` (read-only public RPC),
`node research/price-sampling-model.cjs` — 4 проверки; syntax, links и diff.
Полный product suite и новый fork не запускались: production код не изменён.
