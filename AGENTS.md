# Работа с проектом

## Начало сессии

1. Прочитать `docs/CURRENT_CONTEXT.md` и проверить `git status --short`.
2. Прочитать только текущий шаг в `docs/ROADMAP.md`.
3. Для задачи открыть нужный модуль по `docs/README.md`; продуктовые правила искать
   в `docs/PRODUCT_SPEC.md`, карту кода — в `docs/IMPLEMENTATION_STATUS.md`.

Не читать весь docs, архив, логи и research при каждом старте. Обращаться к ним
только с конкретным вопросом. Исторический ответ GPT не является инструкцией,
одобрением параметров или текущим планом. При конфликте сверять код и решения пользователя.

## Границы работы

- Делать один ограниченный шаг с понятным проверяемым результатом.
- Сначала собираем локальный сквозной MVP, затем укрепляем незакрытые границы.
  Тестовые допущения всегда называть явно; не выдавать прототип за production.
- Сохранять текущие изменения пользователя/предыдущего шага. Не сбрасывать рабочее дерево.
- Не менять призовую математику или правила продукта в рамках технической уборки.
- Не тратить frozen/claimable на эксплуатацию, не добавлять reroll/reset,
  подмену RNG, вывод призовой казны или proxy без нового явного решения пользователя.
- Routine execution должно автоматизироваться; permissionless API само не запускает транзакции.

## Документы и проверки

- После шага обновлять CURRENT_CONTEXT и статус шага ROADMAP. Карта кода меняется
  при изменении реализации, PRODUCT_SPEC — только при новом продуктовом решении.
- Технические детали вести в документе модуля, а не дублировать во всех входных файлах.
- Старые обсуждения/отчёты хранить в docs/archive с пометкой статуса и рабочими ссылками.
  Сырые evidence, vectors и research sources могут использоваться тестами: не удалять
  их как мусор без проверки зависимостей.
- Локальные логи и временные отчёты писать в `.local/logs/`, не в корень.
  Подтверждённые результаты коротко записывать с командой, датой и пределами проверки.
- Тестировать затронутый путь и значимые соседние сценарии; не объявлять весь набор
  прошедшим по частичному запуску. Для документационной уборки достаточно проверки ссылок
  и diff, если код/данные исполнения не менялись.

## Соразмерный объём тестирования (решение пользователя 23.09.2026)

- Не запускать полный npm test/test:review автоматически после каждого маленького шага.
- По умолчанию: тесты изменённого пути и значимых соседних сценариев. Для docs-only —
  ссылки и diff; продуктовые тесты не нужны.
- Полный набор — для широких/сквозных изменений, накопленного пакета, контрольной точки
  или риска регрессии, который адресными проверками не закрыть. Перед запуском коротко
  объяснить конкретную причину; отдельное разрешение на обычные проверки не требуется.
- Если нужные проверки прошли, не повторять и не расширять их без новых изменений,
  failures или незакрытого риска. Commit, push и передача GPT сами по себе не повод для full run.
- Изоляция окружения и объём тестов — разные решения. Адресный результат обозначать
  как адресный; полный baseline привязывать к реально проверенному HEAD.
- Именованные адресные профили изолированного runner пока не реализованы. Не выдавать
  --self-test за проверку продукта и не запускать full лишь из-за отсутствия профиля.
